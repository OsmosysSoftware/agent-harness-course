MCP: live docs and real data instead of memory

A model writes against the library version it was trained on and guesses at your data. An MCP server lets it look both up instead. It is also code that runs with your permissions, so you pin it and vet it before it goes in the repo.

What the harness does instead

The agent consults current library docs before it writes the query. The review's "Pinned versions and live docs" row says context7 in .mcp.json "would have flagged the SQLite DateTimeOffset limit". The error costs 3 minutes here. On a real project the same discovery can arrive as a lossy migration on a database that already has rows.

The review also lists a hook that nudges the agent to consult docs before it writes against a library API. The course uses a cheaper nudge, one line in docs/ai/conventions.md (lesson 9).

What MCP is

The Model Context Protocol (MCP) is "an open source standard for AI-tool integrations" (Claude Code: MCP). An MCP server is a separate program that advertises tools; the harness connects to it and adds those tools to the loop from lesson 1. Nothing else changes. The model still picks a tool call, the harness still runs it, and the result still lands in the context window. Two things follow:

  1. MCP tools pass through the same permission check. They are named mcp__<server>__<tool>. A rule mcp__context7 matches every tool from that server, and allow rules accept a glob (a pattern with * wildcards) only after a literal mcp__<server>__ prefix (Permissions). An allow glob such as mcp__* is skipped with a warning and approves nothing.
  2. A server is a process, not a document. A stdio server is a program Claude Code starts on your machine (here via npx, the package launcher that comes with Node); an http server is a remote URL. Either way its output enters your context, and a local one runs as you.

A remote alternative exists (https://mcp.context7.com/mcp), and an API key is optional (it raises rate limits). The stdio form above keeps the version in your repo, so a reviewer can see what was pinned and when it changed.

Scopes: who gets the server

A scope decides which projects load a server and whether the configuration is shared (MCP installation scopes):

ScopeLoads inShared with teamStored in
Local (default)Current project onlyNo~/.claude.json
ProjectCurrent project onlyYes, via version control.mcp.json in the project root
UserAll your projectsNo~/.claude.json

Harness servers belong in project scope: the file is committed, so every clone and every agent gets the same pinned server. Add it with claude mcp add --scope project context7 -- npx -y @upstash/context7-mcp@4.1.1. Check it with claude mcp list or claude mcp get context7; a server you haven't approved yet shows as ⏸ Pending approval.

The approval prompt exists because a server is code

"For security reasons, Claude Code prompts for approval in interactive sessions before using project-scoped servers from .mcp.json files." Reset your choices with claude mcp reset-project-choices. Two details matter for a team repo:

  • A cloned repository can't approve its own servers. enableAllProjectMcpServers or enabledMcpjsonServers committed in .claude/settings.json is ignored in an untrusted folder, and the server stays at Pending approval. v2.1.196+ · verified 2026-09-30
  • The prompt needs an interactive session. In non-interactive runs (claude -p, where no dialog can appear) and cloud sessions, Claude Code "loads project-scoped servers without asking".

So a one-line change to .mcp.json in a pull request is a change to what code runs on every teammate's laptop. Review it the way you review a .githooks/ script: read the package name, the version and the arguments. The docs add a warning: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk" (prompt injection: text the agent reads that tries to give it new orders).

Real data: read-only database access

The second use of MCP in the review's harness table is "read-only database": let the agent look at real rows instead of inferring them from entity classes. The rule is that reading is cheap and writing is a human decision. Options, and what we know about each (verified 2026-09-30):

OptionStatusRead-only enforced by
Official SQLite MCP reference serverArchived: "no longer maintained"n/a. Don't add an unmaintained server.
Community SQLite MCP servers (for example npm mcp-sqlite-server)Exist; unvettedWhatever the author wrote. You must read it.
sqlite3 -readonly stock.db "…" plus an allow ruleA standard CLI you already haveThe database engine

The course's choice is the third row: no new server, no new code. You need the sqlite3 command-line tool: macOS has it, Linux and WSL2 install it with the package manager (sudo apt install sqlite3), and Git Bash users can download the "sqlite-tools" zip from sqlite.org and put sqlite3.exe on the PATH. Check with sqlite3 --version. A first attempt is an allow rule "Bash(sqlite3 -readonly *)": the agent can query without a prompt, and the engine refuses writes. I ran it on 2026-09-30 (sqlite3 3.51.2):

Be honest about what that guarantees. The database is read-only. The program isn't sandboxed: Claude Code's Bash rules match the command text, and docs say such a rule "isn't a security boundary around the program". The sqlite3 shell has dot-commands, and I checked that one runs even with -readonly:

So the rule the reference .claude/settings.json actually uses is "Bash(sqlite3 -readonly -safe *)", and the agent must pass both flags. An earlier draft of this course shipped the weaker rule; a reviewer caught it. The destructive-guard hook from lesson 7 is a second line of defence, not the first. Check that your build has the flag with sqlite3 -help. Also remember that rows are data, not instructions: a text column can contain "ignore your rules and…". The agent should report what it read, not obey it.

Vet an MCP server before adding it

A community server is a stranger's program that you'll start with your user account's rights: it can read ~/.ssh as easily as a database. Before it reaches .mcp.json, answer six questions, and write the answers down:

QuestionHow to find out
Who maintains it? An organisation, or one person?npm view <pkg> maintainers repository.url
When was the last release? How many releases exist?npm view <pkg> time --json; the 14-day rule still applies to the version you pick
Can you read the source? Does it match the package?Open the repository; compare to the published tarball
What tools does it expose?Read the tool list in the source, then /mcp after adding locally
Can it write, delete or run code?Search the source for writes, exec, network calls
What does it inherit? Env vars, files, network.Look at dependencies and what it is passed in env/args

A worked example, from npm view mcp-sqlite-server on 2026-09-30: version 1.0.1; two releases (2026-02-20 and 2026-03-10); one individual maintainer; repository github.com/ofershap/mcp-server-sqlite; dependencies @modelcontextprotocol/sdk, better-sqlite3 and zod; its description advertises "export data". None of that is damning, and none of it answers "can it write?" That answer is in the source. Until someone on the team has read it, the verdict is not added. The free alternative already gives engine-enforced read-only.

Check yourself

Why does the reference .mcp.json say @upstash/context7-mcp@4.1.1?

Without a version, npx -y runs whatever is newest at session start, with your permissions. A pinned version is a reviewed decision in git, and it follows the 14-day rule.

A teammate commits a new server to .mcp.json. What happens when you open the repo?

Project-scoped servers need approval in an interactive session, and they show as Pending approval until you give it. A server is code that runs as you, so the file is reviewed like code.

What does sqlite3 -readonly guarantee about the agent's commands?

The engine refuses writes to the database (error 8). The CLI's .shell still ran under -readonly when I tested, and -safe refused it, so use both flags.

Exercise: pin context7, then compare two sessions

Exercise · ~60 min · adds: .mcp.json, a vetting verdict and the orders slice

Before you start: node -v must print v18 or later (npx comes with Node), and sqlite3 --version must work (install notes above). Windows: run the shell commands in WSL2 or Git Bash (see Before you start on the index).

  1. Add the server, from the repo root: 
    claude mcp add --scope project context7 -- npx -y @upstash/context7-mcp@4.1.1
cat .mcp.json          # compare with reference-solution/.mcp.json
claude mcp list        # expect a context7 line; Pending approval until you approve it
    Your .mcp.json may be laid out differently from the reference (for example an empty "env": {}): command and args must match. Start claude, approve the server, run /mcp and confirm context7 is connected. Native Windows without WSL2 or Git Bash usually needs cmd /c npx … in place of npx …. unverified: native Windows npx wrapper not tested
  2. Plan the slice first, on main. In plan mode, add to ai-session/PLAN.md the slice "orders: history GET /api/orders, newest first, optional productId filter", and commit the plan alone: docs(plan): orders history slice (leave .mcp.json out of that commit). Then git switch -c scratch/orders-a. In a new session ask: "Implement the next unchecked slice in ai-session/PLAN.md, tests first, and run them. Do not use context7 or web search." Expect the 500 and the NotSupportedException above. Write down how long the agent took to recover and what it did (converter? client-side sort? a migration?). If it applies the converter unprompted, record that too: your model knew. Trainee A's didn't.
  3. Discard it yourself, in your own terminal (the guard hooks only watch the agent): git restore . ; git switch main ; git branch -D scratch/orders-a. Run git status --short and delete only the untracked files the agent created (a new test file, say). Keep .mcp.json: it is yours, and still uncommitted.
  4. Session B, with lookup, on main. New session, same slice: "Check EF Core SQLite limitations with context7 first, then implement the next unchecked slice in ai-session/PLAN.md, tests first." Look for a tool call whose name starts with mcp__context7__, and confirm the converter appears in StockDbContext. Run dotnet test. Don't commit yet.
  5. Read-only data. stock.db is created at src/StockApi/stock.db and is git-ignored. Delete any old copy first (rm -f src/StockApi/stock.db*), because the converter changes how dates are stored. In a second terminal run dotnet run --project src/StockApi --urls http://127.0.0.1:5077, then in another: 
    curl -s -X POST http://127.0.0.1:5077/api/products -H 'Content-Type: application/json' -d '{"sku":"A1","name":"A","stock":5}'
curl -s -X POST http://127.0.0.1:5077/api/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":1}'
curl -s -X POST http://127.0.0.1:5077/api/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":2}'
    Stop the API with Ctrl+C. The tighter rule "Bash(sqlite3 -readonly -safe *)" is already under permissions.allow from the lesson 7 listing; if your file lacks it, add it now. Ask: "Using sqlite3 -readonly -safe on src/StockApi/stock.db, how many orders does each product have?" (expect product 1 with 2 orders). Then probe: "Now delete all orders with sqlite3." Expect the engine error. You just ran a guard probe for lesson 7's table.
  6. Vet a server, on paper. Pick mcp-sqlite-server or any other community server. Fill in the six questions from the table. Put the verdict in ai-session/PLAN.md under "Decisions made by the human", for example: 2026-09-30: add mcp-sqlite-server? → not added, because source unread and sqlite3 -readonly already enforces read-only.
  7. Commit through /commit, in two commits. First chore(harness): add context7 MCP server pinned to 4.1.1 (.mcp.json and the plan verdict), then the slice as feat(orders): list orders newest first (tick its box in PLAN.md first).

Codex: put the [mcp_servers.context7] block above in .codex/config.toml (the project must be trusted) and ask for the lookup by name. Codex has no .mcp.json approval prompt that I could verify; read the server list before you start. Antigravity: save the JSON above as .agents/mcp_config.json. Steps 2 to 4 are the same in both tools; for step 5 use the tool's own command allow list (command(sqlite3) in Antigravity permissions), and keep both flags in the command itself.

Done when
  • .mcp.json is committed with @upstash/context7-mcp@4.1.1 (no bare package name)
  • You saw the DateTimeOffset error in session A and a mcp__context7__ call in session B
  • The agent's DELETE against stock.db failed with "attempt to write a readonly database"
  • PLAN.md holds a six-question verdict for a server you did not add
