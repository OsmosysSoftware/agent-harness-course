MCP: live docs and real data instead of memory

A model writes code against the library it saw in training, and guesses at the rows in your database. An MCP server gives it a tool to look both up. It is also a program that runs with your permissions, so you vet it, pin it and approve it first.

12 min read 60 min exercise Plaque: Live Docs
In 30 seconds
  • An MCP server adds tools to the agent's loop. context7 adds "look up current library docs".
  • It helps only if the agent calls it, so you ask for the lookup in the prompt and the rules. A passing test is still the proof.
  • For data, you don't need a new server: sqlite3 -readonly -safe through Bash, where the database engine refuses writes.

What happened

Failed run

The slice: GET /api/orders, newest first. The obvious query sorts on CreatedAt, a DateTimeOffset. It compiles. The endpoint answers 500, and the response body says only "An error occurred while processing your request". The API's log has the reason:

System.NotSupportedException: SQLite does not support
expressions of type 'DateTimeOffset' in ORDER BY clauses.

Reproduced on the course's reference app, 2026-10-01

With the harness

The agent asks the docs before it writes the query. The EF Core docs, fetched through context7, say that on SQLite, DateTimeOffset "comparison and ordering will require evaluation on the client". So it stores the column in a type SQLite can sort:

GET /api/orders → 200, newest first
dotnet test     → green

The lookup costs one tool call. The 500 costs a debugging loop, or on a real project a data migration.

What MCP is

The Model Context Protocol (MCP) is "an open source standard for AI-tool integrations" (Claude Code: MCP). An MCP server is a separate program that tells the harness which tools it offers. Think of it as a plug: the loop from lesson 1 stays the same, and it just has more tools to call.

Two things follow. MCP tools are ordinary tools to the permission system: a rule mcp__context7 matches every tool from that server (Permissions). And a server is a process, not a document. This one is a stdio server: a program Claude Code starts locally and talks to over its input and output. It can do whatever your user account can do.

context7: today's docs, pinned

context7, maintained by Upstash under the MIT licence, "pulls up-to-date, version-specific documentation and code examples straight from the source". This is the course's .mcp.json:

The @4.1.1 is the important part. Without it, npx -y downloads and runs whatever version is newest, every time a session starts. Pinning means naming one exact version, so nothing new runs on your machine until someone changes that line in a reviewed commit. The version also follows lesson 7's 14-day rule: 4.1.1 was published on 2026-09-14, 17 days before this lesson was checked (npm view @upstash/context7-mcp time). context7-mcp 4.1.1 · verified 2026-10-01

You put it in project scope, which writes .mcp.json in the repo root. Everyone who clones the repo gets the same pinned server. That is also why Claude Code asks first: "For security reasons, Claude Code prompts for approval in interactive sessions before using project-scoped servers from .mcp.json files." So a one-line change to .mcp.json in a pull request changes what runs on every teammate's laptop. Review it like a git hook script.

Making the agent use it

A connected server is only a capability. The agent still has to decide to call it, and a model that is sure it remembers an API often won't. Here is the same slice, done both ways:

Two places to ask for the lookup, both in files or prompts you control:

  1. In the prompt, for the slice at hand: "Check the EF Core SQLite limitations with context7 before you write the query."
  2. In the rules, for every session. Lesson 9's docs/ai/conventions.md gets the line "For any library API you are not sure of, look it up (context7 MCP) instead of relying on memory", and records today's answer so the next session doesn't need the lookup.

A lookup is not a guarantee: the agent can skip it, pick the wrong library or misread the result. Nor does it prove the code works. The test ListOrders_MultipleOrders_ReturnsNewestFirst, on real SQLite, does that.

Real data, read-only

The other thing an agent guesses at is your data. Let it read real rows instead of inferring them from entity classes: reading is cheap, writing is a human decision. No MCP server needed, because lesson 7's settings already allow one command:

"Bash(sqlite3 -readonly -safe *)"

Each flag does a different job, and we checked both (sqlite3 3.51.2, on a copy of stock.db):

-readonly makes the engine refuse writes, but the sqlite3 program's dot-commands still work, and .shell runs any command. -safe "attempts to disable all features of the CLI that might cause any changes to the host computer" other than that database file: .shell, .output and ATTACH were all refused when we tried them (sqlite3 CLI). Without both flags the allow rule doesn't match, so you get a prompt. And remember that rows are data, not instructions: a text column can say "ignore your rules". The agent reports what it read, and doesn't obey it.

Vet a server before you add it

A community server is a stranger's program, started with your account's rights: it can read ~/.ssh as easily as a database. Before it reaches .mcp.json, answer these and write the answers down:

Check yourself

Why does .mcp.json say @upstash/context7-mcp@4.1.1 and not just the package name?

Without a version, npx -y runs whatever is newest at session start, with your permissions. A pinned version is a reviewed decision in git, and it follows the 14-day rule.

context7 is connected and approved, yet the agent writes the DateTimeOffset sort from memory. Why?

The model decides which tools to call. Ask for the lookup in the prompt and in the rules, and let the test prove the result.

What does sqlite3 -readonly on its own guarantee?

The engine refuses writes to the database (error 8), but .shell still ran under -readonly. -safe refused it, so the rule and the command carry both flags.

Exercise: vet, pin, then compare two sessions

Exercise · about 60 min · you add: .mcp.json, two vetting verdicts, the orders history slice

Work in your practice repo (~/projects/stockapi), with everything from lessons 1 to 7. You need Node 18 or later for npx (node -v) and the sqlite3 command (sqlite3 --version; on Linux or WSL2, sudo apt install sqlite3). Windows: use WSL2 or Git Bash (setup).

  1. Start clean. git status is clean and you are on main. Run grep -rn DateTimeOffset AGENTS.md docs tests .claude: it should print nothing. If it finds a rule about it, the agent will likely get step 6 right first time. Note that, and carry on.
  2. Vet before you add. Run the npm view commands from the table for @upstash/context7-mcp, and check that 4.1.1 is at least 14 days old. Then do the same, on paper, for a community SQLite MCP server you find on npm. Under "Decisions made by the human" in ai-session/PLAN.md, write one line each, for example: 2026-10-01: context7 4.1.1 → added: Upstash, MIT, 17 days old, docs only. <sqlite server> → not added: source unread, and sqlite3 -readonly -safe already covers reads.
  3. Add it at project scope and approve it. 
    claude mcp add --scope project context7 -- npx -y @upstash/context7-mcp@4.1.1
cat .mcp.json
claude mcp list
    Expect the JSON above (plus an empty "env": {}), and context7: … ⏸ Pending approval (run `claude` to approve). The -- separates Claude's options from the server's command. Start claude, approve the server, then run /mcp: context7 should show as connected.
  4. Commit it. Stage .mcp.json and ai-session/PLAN.md, then /commit, for example chore(harness): add context7 MCP server pinned to 4.1.1.
  5. Plan the slice. In plan mode, add to ai-session/PLAN.md: "orders: history GET /api/orders, newest first, optional productId filter (tests: order, filter)". Stage only that file and /commit it alone: docs(plan): orders history slice.
  6. Session A, from memory, on a scratch branch. git switch -c scratch/orders-a, start a fresh session and ask: "Implement the next unchecked slice in ai-session/PLAN.md, tests first, and run them. Do not use context7 or web search." Expect a failing test with a 500, and the NotSupportedException when the agent digs in. Write down what it did about it: a converter, sorting in memory, something else? If it used the converter without being told, write that down too. Your model knew, but you can't count on it knowing.
  7. Throw it away, yourself, in this order: git restore ., git switch main, git branch -D scratch/orders-a. Then git status --short, and delete any untracked file the agent created (a new test file, say).
  8. Session B, docs first, on main. Fresh session: "Check the EF Core SQLite limitations with context7 before you write any query, then implement the next unchecked slice in ai-session/PLAN.md, tests first." If Claude asks before an mcp__context7__… call, approve it. Read what came back. Confirm the fix is in StockDbContext and that dotnet test is green. Don't commit yet.
  9. Real data. The database lives at src/StockApi/stock.db and is git-ignored. Delete any old copy, because the converter changes the column type: rm -f src/StockApi/stock.db src/StockApi/stock.db-shm src/StockApi/stock.db-wal. In a second terminal, dotnet run --project src/StockApi --urls http://127.0.0.1:5077. In a third: 
    curl -s -X POST http://127.0.0.1:5077/api/products -H 'Content-Type: application/json' -d '{"sku":"A1","name":"A","stock":5}'
curl -s -X POST http://127.0.0.1:5077/api/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":1}'
curl -s -X POST http://127.0.0.1:5077/api/orders -H 'Content-Type: application/json' -d '{"productId":1,"quantity":2}'
curl -s http://127.0.0.1:5077/api/orders
    The last line should list order 2 before order 1. Stop the API with Ctrl+C. Ask the agent: "Using sqlite3 -readonly -safe on src/StockApi/stock.db, how many orders does each product have?" Expect product 1 with 2 orders, and no permission prompt. Then: "Now delete all orders, with sqlite3 -readonly -safe." Expect attempt to write a readonly database (8). If it tries a different command, you get a prompt: say no. If it declines to try at all, run that command yourself and read the error.
  10. Review and commit. Follow your workflow: /quality-gate, the reviewers from lesson 6, tick the slice in PLAN.md, then /commit, for example feat(orders): list orders newest first.

Codex: put the [mcp_servers.context7] block in .codex/config.toml (the project must be trusted) or use codex mcp add, and ask for the lookup by name. Antigravity: save the JSON as .agents/mcp_config.json; MCP tools ask before they run by default. In both, keep both sqlite3 flags in the command itself.

Done when: tick all four to earn the Live Docs plaque
  • .mcp.json is committed with @upstash/context7-mcp@4.1.1, and /mcp shows it connected
  • You saw what session A did without docs, and a mcp__context7__ call in session B before its query
  • The agent counted orders with sqlite3 -readonly -safe, and its DELETE failed with "attempt to write a readonly database"
  • PLAN.md holds both vetting verdicts, and feat(orders) is committed with dotnet test green
