Skills: procedures the agent runs by name

A skill is a versioned procedure in your repo that the agent loads and follows step by step. It isn't a prompt you paste again each time, so the steps stay the same on every run and for every trainee.

Recall

You typed a rule in chat, then ran /compact. Which rule is most likely to survive?

Project-root rules files are re-read from disk after compaction. Anything said only in conversation is summarised and may be lost (lesson 1).

The test provider cannot run the atomic stock update. What does the 1-3-1 rule make the agent do?

1-3-1 means one problem, three options, one recommendation, then wait. The choice belongs to the human (lesson 3).

The win

By the end you'll have a /commit skill and a /quality-gate skill in your repo, visible to Claude Code, Codex and Antigravity. You'll also have seen the commit skill refuse a build-output file, and you'll have committed the skills themselves through it.

What the harness does instead

Templates become skills the tool discovers and runs by name, written for this repo and reviewed in a diff like code. "Test everything" becomes /quality-gate: a script that runs format, build and test and stops at the first failure.

A skill is a procedure, not a pasted prompt

A skill is a folder containing a SKILL.md file: YAML frontmatter, then instructions in Markdown. Claude Code loads the skill's name and description into context at the start, and loads the full body when the skill is invoked, either by you typing /name or by the model choosing it from the description. Custom commands have been merged into skills: a file in .claude/commands/ and a skill in .claude/skills/ both create the same slash command (Skills).

Three differences from a pasted prompt matter for the harness:

  1. It lives in git. A change to the procedure is a reviewed diff, and everyone who clones gets it. Trainee C's templates lived in a chat window and went stale unnoticed.
  2. It loads on demand. Only the name and description sit in context all the time, which keeps the window small. The body enters the conversation when the skill runs (the same page explains the lifecycle).
  3. It can carry code. A skill folder can hold supporting files, such as a script, that the instructions tell the agent to run. The script's logic then isn't re-invented by the model on each run. quality-gate does exactly this with gate.sh.

All frontmatter is optional and description is recommended (frontmatter reference). The docs warn that a project skill can grant itself broad tool access through allowed-tools, so review that field in any skill you clone (pre-approve tools).

The trade-off on disable-model-invocation. Leaving it off lets the agent run commit itself when your rules say a slice is done; setting it forces a human to type /commit each time. The course leaves it off, because the harness should steer the agent without the human typing every step, and puts the human approval inside the skill (step 6) and behind an ask rule (lesson 7). If your team wants the stricter form, add the one line. The description is still what decides auto-invocation for every skill that doesn't set it. The description text in the skill listing is cut at 1,536 characters, which is why the key use case goes first.

Where the files live: one folder, three tools

Claude Code looks for project skills in .claude/skills/<name>/SKILL.md. Codex and Antigravity both read .agents/skills/<name>/SKILL.md (see the table below). To write each skill once, keep the real folder in .agents/skills/ and add a per-skill symlink (a tiny file that points at another path) in .claude/skills/. The Claude Code docs support this: "a <skill-name> entry in the enterprise, personal, or project location can be a symlink to a directory elsewhere on disk" (Skills).

The link target is relative to the link's own folder, which is why it starts with ../../. Use one link per skill, not one link for the whole .claude/skills folder, so a Claude-only skill can still sit beside them later. Git stores a symlink as a tiny file holding the path, so the link travels in the repo.

Windows. In WSL2 the commands above work unchanged. In Git Bash, ln -s may quietly make a copy instead of a link, or git may write the link as a plain text file, and then Claude Code finds no skill. If ls -l doesn't show ->, copy the skill folders instead and re-copy after every edit, so you know there are two copies to keep in step. unverified: Git Bash symlink behaviour is standard git and MSYS behaviour, not checked against the tool docs

Gotcha: a personal skill with the same name wins

When two skills share a name, the location decides: "Enterprise over personal, and personal over project. With deploy in both ~/.claude/skills/ and the project's .claude/skills/, /deploy runs the personal one" (Resolve skills that share a name). If you already have a personal ~/.claude/skills/commit, it silently replaces the repo's commit, with no warning and none of the steps below. Run ls ~/.claude/skills now, and rename or remove a clash. The same applies to whoever runs your repo in the swap test in lesson 11: that run should use a clean profile.

The commit skill, step by step

This is the reference solution's commit skill, verbatim. Read it as a checklist the agent cannot forget to load, because the body is in context the moment the skill runs. Each numbered step below it is tied to a failure from the review.

Two terms in that file. Conventional Commits is a convention for commit subjects, type(scope): summary such as feat(products): add low-stock endpoint, so history reads as a list of changes (spec). gitleaks is a command-line scanner that looks for passwords and API keys in code (install page). No gitleaks? Do the pattern half of step 3 only; the skill says "if installed", and lesson 7 adds a git hook that warns when it is missing.

Two design choices are worth copying. First, every refusal ends in an action for the human ("propose git restore --staged", "ask the human to run git config"), so the agent has somewhere to go that isn't a workaround. Second, step 5 says "from the diff, not from memory". Trainee F's 908d6fa described the last thing the agent did, not what was in the commit.

The quality gate: a skill that carries a script

"Test everything yourself" asks the model to remember which commands to run, in which order, and to stop when one fails. quality-gate moves that into a script, and the skill only says when to run it and what to do with the result.

  • set -euo pipefail plus || { …; exit 1; } makes the first red step stop the run with a message that names the step.
  • cd "$(git rev-parse --show-toplevel …)" makes it work from any folder in the repo.
  • Your starter repo has no .editorconfig, so step 1 checks against the .NET defaults. It still catches the stray indentation you'll add in the exercise.
  • .gitattributes is already in your repo: it keeps scripts LF so bash works on Windows checkouts.
  • The path is repo-relative, not ${CLAUDE_SKILL_DIR} (a Claude Code variable the docs describe), so Codex and Antigravity can run the same command.
  • The skill body holds the judgement the script can't: never delete, skip or weaken a test to get green, and after two failed fixes use 1-3-1. That's Trainee D's InMemory rewrite, forbidden in a sentence.

Why a skill is still only a request

A skill is text the model reads. It can skip step 3, run steps out of order, or never load the skill at all if it decides the description doesn't match. The review calls this out for Trainee F: "Test everything yourself" was a request, not a gate. A skill raises the odds a lot because the steps are specific and in context, but it doesn't block anything.

That's why the harness has layers. Lesson 7 backs each skill step with something the harness enforces:

Exercise: add the two skills, then commit them through /commit

Exercise · ~60 min · adds: .agents/skills/commit, .agents/skills/quality-gate, and the skills in your workflow rules

You are in your practice repo, which already has AGENTS.md and the plan workflow from lessons 2 to 4. The skills are the next piece of harness, still before any new feature code.

  1. Set your identity first. The commit skill refuses any email that isn't a company address. Run git config user.email you@osmosys.co (your own address), then git config user.email should print it.
  2. Ask the agent to write the skills from the spec, not from a copy. Prompt: 
    Create two skills in .agents/skills/ (tool-neutral location).
1. commit: steps to see staged files (never git add -A), refuse bin/ obj/ tmp/ .db .env,
   scan for secrets, check the git user.email ends in @osmosys.co, draft a Conventional
   Commit from git diff --cached with no AI attribution, show it and wait for my yes,
   then commit. Never push.
2. quality-gate: a gate.sh that runs dotnet format --verify-no-changes, dotnet build
   -warnaserror, dotnet test --no-build, stopping at the first failure; plus a SKILL.md
   that says to fix, never weaken a test, and use 1-3-1 after two failed attempts.
Write the descriptions so each skill is chosen at the right moment. Do not commit.
    Compare its result with the two listings above. Keep your version if it covers every step; if it misses one (often step 4 or the "no git add -A" rule), ask it to add it.
  3. Check for a name clash first: ls ~/.claude/skills. A personal commit or quality-gate there would win over the repo's. Then make Claude Code see them. From the repo root run the ln -s commands above (Windows: in WSL2 or Git Bash; if Git Bash makes copies, copy the folders instead), then ls -l .claude/skills. Start a new session and type /; both names should appear. Check that Claude Code follows the symlink before you rely on it.
  4. Run /quality-gate. Claude Code will ask permission for bash …/gate.sh and dotnet format: answer "Yes" once each, not "Yes, and don't ask again", because lesson 7 writes the real rules. Expect three steps and "quality gate: green". If dotnet format fails on the starter files, that's the skill working: let the agent run dotnet format and re-run.
  5. Break it on purpose. Add three spaces of indentation to one line in src/StockApi/Program.cs and run /quality-gate again. It must stop at step 1 with "GATE FAILED at format" and not reach build. Revert the edit.
  6. Make /commit refuse. Run dotnet build, then force-add a build file: git add -f src/StockApi/obj/project.assets.json (any file under obj/ works). Run /commit. It should stop at step 2, list the path, and propose git restore --staged. Run the restore it proposes.
  7. Commit the skills through the skill. Ask /commit to stage the two skill folders and .claude/skills. You should see the file list and a drafted message such as feat(harness): add commit and quality-gate skills, then a question. Answer yes. Check git log -1 --format='%h %an <%ae>%n%B': company email, no AI trailer.
  8. Point your rules at the skills. In docs/ai/workflow.md your steps 4 and 6 are still manual (run the tests by hand, write the commit message by hand). Edit them to name the skills: step 4 "run the quality-gate skill", step 6 "run the commit skill; it drafts the message and waits for approval". Make the same swap in the Definition of done in AGENTS.md: the "format check, build and test pass" item becomes "the quality-gate skill passes", and the commit approval item names the commit skill. Leave step 5 (review) manual until lesson 6. Commit the two files through /commit: docs(ai): point workflow at skills.
  9. Write one sentence: which step of the commit skill could the agent skip, and what would notice? (Lesson 7 answers it.)

Codex: skills in .agents/skills/ are read as they are, so skip the symlinks. Start a new session and type $commit or $quality-gate. Codex may or may not add a co-author trailer by default unverified, so check the message of this first commit. Antigravity: the same folder works, invoked as /commit. If you have Antigravity workflows (path unverified), convert them with /migrate-workflows.
