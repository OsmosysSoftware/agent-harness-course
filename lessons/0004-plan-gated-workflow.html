The plan-gated workflow

Explore, plan, let the human edit the plan and commit it alone, then build one small slice at a time, so you find the wrong idea in a page of text instead of in sixty files.

Recall

Lesson 2: when does a Claude Code path-scoped rule load?

A rule with paths: frontmatter triggers when Claude reads a file matching the glob. A rule without paths loads always. That is why invariants that must hold everywhere live in the root file.

Lesson 3: after presenting its 1-3-1, what should the agent do next?

The format ends with "then wait for the human's decision". Acting on the recommendation early is just the silent decision again, with better manners.

The win

By the end, ai-session/PLAN.md is committed on its own before any code. The low-stock endpoint has been built as one slice. A requirement that arrives halfway has gone through a plan change first, in its own commit, before it became code.

What the harness does instead

The gate is written into docs/ai/workflow.md and loaded every session, so the next person (or the next you) gets it without retyping it. Their two rejections become what the assessment grades: "Evaluated on what they changed, not on the plan's length."

The loop

The workflow is a file, so every agent reads the same one. The reference version, from docs/ai/workflow.md:

Three steps are gates, which means they stop the work until a human acts: plan approval (step 2), review (step 5) and commit approval (step 6). Steps 4 to 6 use things you build in the next two lessons: the quality-gate and commit skills (lesson 5) and the reviewer subagents (lesson 6). In your own workflow.md, write steps 4 to 6 as manual for now: "4. Run dotnet test. 5. The human reviews the diff. 6. The human approves the commit message, then commit." Lessons 5 and 6 swap in the skill and reviewer names. Never point your file at a skill that does not exist yet.

Why a plan file and not just "plan mode"? Plan mode is a tool state; PLAN.md is a contract. The first is gone when the session ends. The second is in git, diffable, editable by you in your editor, readable by a different agent tomorrow, and it has a timestamp that predates the code.

Plan mode, in three tools

Plan mode is a permission mode where the agent explores but cannot change your source. In Claude Code, press Shift+Tab until the line under the input box shows ⏸ plan mode on, or start with claude --permission-mode plan. "Claude reads files and answers questions without making changes", and you leave plan mode by approving the plan or pressing Shift+Tab (Best practices: explore first, then plan, then code). Press Ctrl+G to open the proposed plan in your editor (if that does nothing, skip it and edit the file in step 4) and change it before Claude proceeds (Permission modes). The plan Claude wrote in plan mode is re-injected from disk after compaction (Context window). A /plan prefix on a single prompt also works.

The plan file

The plan file is deliberately small. The reference template, as it stood after two slices:

SectionWhat it is for
Approved byYour name and the date. It is the human act that the gate is about; an unsigned plan is just the agent's draft.
SlicesOne checkbox per commit. Each names the test that proves it and the behaviour it must have. The agent implements "the next unchecked slice" and nothing else.
Decisions made by the humanThe 1-3-1 answers from lesson 3, with reasons. This is the record of what you decided, as opposed to what the agent did.
Changes to this planThe audit trail for mid-task changes (next section). Each entry matches a docs(plan): … commit.

What to change in the agent's plan

The agent's first draft will look reasonable, and it is usually the first draft you should distrust. Read it against this checklist and change something. A plan you approved without editing is a plan you didn't read:

  • Slices too big. "Implement orders and alerts" is three commits. Split until each slice is one behaviour with one test, small enough to read in a diff.
  • No test per slice. Every slice needs the test that would fail if the feature broke, named in the plan. A slice with "add tests later" is not a slice.
  • Scope creep. Anything not in BRIEF.md: extra filters, persisted rejected orders, an auth layer. Delete it, as Trainee A did. The scope rule is in docs/ai/invariants.md: "Endpoints are exactly those in BRIEF.md plus the ones a human-approved plan adds."
  • An invariant is not mentioned. A slice that touches stock must say it keeps the guarded UPDATE and the concurrency test green. If the plan does not mention the invariant, add it; the reviewer agent will check it later.
  • Files it will touch are missing. If the plan does not list them, it has not looked at the code.

When requirements change

Real projects change halfway through. The workflow's rule: "Stop the current slice. Update PLAN.md (add, change or remove slices, with the reason), get the human's approval, and commit the plan change on its own. Then continue. Never absorb a new requirement into a slice silently." The assessment plants exactly this: at the 1:30 mark, a message arrives saying "alerts must also be resolvable manually". The expected behaviour is "Plan updated and re-approved before code; the change lands as its own slice."

Why a separate commit for the plan change? Same reason as the first plan: the history then shows the change was decided before it was built, and whose decision it was. Squashing the change into the slice hides that, and makes the slice's diff impossible to review against the plan you approved.

Scope bait

The same set of planted traps includes a brief that says auth is "out of scope for now". The right behaviour is that scope written into the rules file makes the agent decline the suggestion. Trainee C added JWT login and AI triage although the brief did not ask, and a doc claimed JWT was "rejected" one minute before it was committed. In this course the defence is two lines: Out of scope: auth, UI, payments. Decline and say so if asked to add them. in AGENTS.md, and the scope section of docs/ai/invariants.md. You will test it with a deliberate bait prompt in the exercise.

Check yourself

Where and when should the approved plan file be committed?

A plan that shares a commit with the code cannot prove it came first; that was Trainee D's 1009656. Committed alone, git timestamps show the plan was approved before the work.

Halfway through, a partner asks for a new filter. What does the workflow do first?

A new requirement is a plan change: add or change slices with the reason, get approval, commit the plan change alone, then build it as its own slice. Declining applies to things the brief excludes, like auth, not to a partner's brief change.

A draft plan has one slice: "implement low-stock endpoint and alerts". What should you change?

Slices that are too big are the first item on the checklist. One behaviour and one named test per slice keeps each commit reviewable and gives the gate something small to check.

Exercise: plan, gate, build one slice, then absorb a change

Exercise · ~45 min · adds: ai-session/PLAN.md and the low-stock endpoint

The feature: GET /api/products/low-stock?threshold=, which returns products whose stock is at or below the threshold. You decide the details in the plan; that is the exercise.

  1. Fill in the workflow doc. Windows: run the commands in WSL2 or Git Bash (see Before you start on the index). Lesson 2 left docs/ai/workflow.md as a stub. Ask the agent to fill it in, adapting the reference version quoted above, with steps 4 to 6 manual as described there. Keep the "When stuck" and "Git rules" sections. Read every line and change what your repo doesn't match. Commit it alone, before the plan: 
    git add docs/ai/workflow.md
git commit -m "docs(ai): workflow"
  2. Plan mode. Start a fresh session, switch to plan mode, and check the "AGENTS.md loaded" line (missing? look for a stray CLAUDE.local.md, lesson 2). Prompt: 
    Explore ProductsController and the tests first. Then plan a GET /api/products/low-stock?threshold= endpoint: products with Stock <= threshold, ordered by stock then SKU, default threshold 5, 400 for an out-of-range threshold. Propose the valid range. Plan in slices: each with its test and the files it touches. Write no code.
  3. Write it to the file. When the agent shows its plan, Claude Code asks what to do next. Choose the option that keeps manual approval of edits, or keep planning; do not choose an option that auto-accepts edits or starts building. (Press Ctrl+G first to edit the plan, if your editor opens.) Plan mode cannot write your ai-session/PLAN.md, so press Shift+Tab until you have left plan mode, then prompt. If the agent starts editing code instead, press Esc, say "stop, revert that, I only want the plan file", and run git status to check: 
    Write that plan into ai-session/PLAN.md using this structure: Approved by, Goal, Slices (checkboxes, one commit each, with tests), Decisions made by the human (keep what is there), Changes to this plan. Do not write any code.
  4. Edit it like a reviewer. Open the file in your editor. Apply the five-point checklist and make at least one real change: split a slice, add a missing test, pick the threshold range yourself, or delete something the agent added. For example: set the valid range to 0 to 1000 and add a test for 1001 returning 400. Jot down what you changed and why; you will use it in lesson 10. Fill in Approved by.
  5. Commit the plan alone. 
    git add ai-session/PLAN.md
git commit -m "docs(plan): low-stock endpoint"
git show --stat HEAD
    The stat lists one file.
  6. Scope bait. In the same session: "While you're at it, add an API-key check so only staff can call this endpoint." Expect a polite refusal that cites the out-of-scope rule. If it complies, tell it to revert, and note that your rules file needs a stronger line.
  7. One slice. 
    Implement only the first unchecked slice in ai-session/PLAN.md, with its test. Stop when it is done.
    Run dotnet test yourself. Tick the box in ai-session/PLAN.md and commit with a hand-written message, staging exactly the files the slice touched plus ai-session/PLAN.md (the tick): git add <the files the slice touched> ai-session/PLAN.md && git commit -m "feat(products): low-stock endpoint". Only the plan-change commits are plan-only. git commit -a skips new files, so a new test file would be left out. Lessons 5 and 7 replace this with a skill and a guard.
  8. The mid-task change. Working alone is fine: paste this into the session yourself, as if a partner had just sent it (or have a friend send it): "Low-stock must also accept an optional skuPrefix filter." Give it to the agent as-is. The right response is to stop and update the plan, not to start editing. Then: add a slice to PLAN.md with its test, add a line under "Changes to this plan" with the reason, and approve it. Commit it alone: 
    git add ai-session/PLAN.md
git commit -m "docs(plan): add skuPrefix filter"
  9. The second slice. Implement only the new slice, run dotnet test, tick the box, stage the files the slice touched plus ai-session/PLAN.md, and commit feat(products): skuPrefix filter for low-stock (git add <files> && git commit -m "…", not -a).
  10. Look at your history: git log --oneline. The plan commits should sit directly before the code they govern.

Codex: run with the read-only sandbox for steps 2 and 3 (or say "plan only, no edits"), then switch to the normal mode for the slices. Antigravity: use /plan for step 2 and copy the approved plan into ai-session/PLAN.md. Steps 4 to 9 are identical.

Done when
  • docs(ai): workflow is committed before the plan, and docs/ai/workflow.md is no longer a stub
  • git log --oneline shows docs(plan): low-stock endpoint before feat(products): low-stock endpoint, and git show --stat on the plan commit lists only ai-session/PLAN.md
  • PLAN.md has Approved by filled in and you can name one thing you changed from the agent's draft
  • The agent declined the auth bait citing the scope rule, or you recorded that it didn't
  • docs(plan): add skuPrefix filter precedes the skuPrefix feature commit, and dotnet test is green
