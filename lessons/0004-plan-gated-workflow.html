The plan-gated workflow

Get a plan before any code, edit it yourself, and commit it on its own. Then build one small slice at a time. You catch a wrong idea on one page of text instead of in sixty files.

15 min read 45 min exercise Plaque: Plan Gatekeeper
Recall

Lesson 2: someone adds a CLAUDE.local.md to the repo root. What happens to your AGENTS.md?

By default Claude Code reads AGENTS.md only when there is no CLAUDE.md, .claude/CLAUDE.md or CLAUDE.local.md in the folder or above. One stray file switches your rules off.

Lesson 3: the agent has handed you a 1-3-1. What should it do next?

The format ends with "then wait for the human's decision". Acting on the recommendation early is the silent decision again, with better manners. This lesson applies the same idea to whole features.

In 30 seconds
  • The first thing you ask for is a plan, not code. You edit it and commit it alone.
  • Then one slice per commit: each slice passes its tests and your review before it is committed.
  • A requirement that changes halfway goes into the plan first, in its own commit, then gets built.

What happened

Failed run

A developer's whole instruction was "Please build the whole project for me". There was no plan to read, so there was nothing to correct early.

The result was one 60-file commit whose message said it added tests. Elsewhere, a plan file arrived in the same commit as the whole API, every box ticked, so nothing proved it came first.

Real sessions, anonymised

With the harness

A written workflow: plan first, the human edits it, it is committed alone, then one slice per commit.

One developer worked this way: no code until they had read the plan, two proposals struck as scope creep, and a locking claim proved with a 20-way race test.

Plan mode keeps the agent's hands off

Plan mode is a permission mode where Claude reads, explores and writes a plan, but cannot edit your source until you approve that plan. When auto mode is available, a classifier (a second model) may approve the shell commands it runs to explore; otherwise anything beyond read-only commands asks you. Enter it with Shift+Tab until the status bar shows ⏸ plan mode on, with claude --permission-mode plan, or with a /plan prefix on one prompt (Permission modes) verified 2026-10-01.

The catch is at the end. When the plan is ready, Claude asks how to proceed, and approving exits plan mode and starts editing:

Option in the dialogWhat happens nextUse it here?
Yes, and use auto mode (or "Yes, auto-accept edits")Claude starts building, and edits run without asking youNo: nothing stops it writing code before you have edited the plan
Yes, manually approve editsClaude starts, but every edit asks you firstYes: accept the edit to ai-session/PLAN.md, refuse anything else
No, keep planningStays in plan mode; you say what to changeYes, while the plan is still wrong

Press Ctrl+G in that dialog to open the plan in your editor and change it before choosing. Press Shift+Tab to leave plan mode without approving anything.

Going deeper: why a file, when plan mode already makes a plan?

Plan mode is a tool state. Claude Code does keep its plan across compaction (Context window), but the plan isn't in your repo. ai-session/PLAN.md is a contract: it is in git, you edit it in your own editor, tomorrow's session or a different tool can read it, and its commit is timestamped before the code it governs.

Edit the plan like a reviewer

The agent's draft will look reasonable. Read it with a red pen anyway: a plan you approved unchanged is usually one you didn't read closely.

Also check: a slice that touches stock says it keeps the guarded UPDATE and the concurrency test green, and every slice lists the files it touches.

When the requirement changes

A colleague writes: "Low-stock must also accept an optional skuPrefix filter." Don't fold it quietly into the slice in progress. Stop, update the plan with the reason, approve it, commit that change alone, then build it as its own slice. The history shows the change was decided before it was built.

Scope bait is different: a request for something the brief rules out, such as authentication. A brief change gets a plan change; an out-of-scope request gets a polite no that cites the rule.

Check yourself

When should the approved plan file be committed?

A plan that shares a commit with code can't prove it came first. Committed alone, the history shows it was decided before the work began.

Halfway through a slice, a colleague asks for a new filter that fits the brief. What comes first?

A brief change is a plan change: add the slice with its test and the reason, approve it, commit it alone, then build it. Declining is for things the brief excludes, like auth.

Claude has presented its plan. You want it to write only ai-session/PLAN.md, and nothing without your say. What do you pick?

Approving always exits plan mode and starts editing. "Yes, manually approve edits" makes each edit ask you, so you accept the plan file and refuse the rest.

Exercise: plan, gate, one slice, then a change

Exercise · about 45 min · you add: docs/ai/workflow.md, ai-session/PLAN.md, the low-stock endpoint

The feature: GET /api/products/low-stock?threshold= returns products whose stock is at or below the threshold. Work in your practice repo from lessons 1–3. Windows: use WSL2 or Git Bash (setup).

  1. Fill in the workflow. Ask the agent to fill in docs/ai/workflow.md from the loop above, with steps 4 to 6 manual, plus the "When requirements change" and "When stuck" sections. The retry limit in "When stuck" is what would have stopped the 35-minute Docker polling from lesson 3. Read every line, then commit it alone: 
    git add docs/ai/workflow.md
git commit -m "docs(ai): workflow"
  2. Plan mode. Start a fresh session and press Shift+Tab until you see ⏸ plan mode on. Prompt: 
    Read ProductsController, the tests and docs/ai/ first. Plan GET /api/products/low-stock?threshold=:
products with Stock <= threshold, ordered by stock then SKU, default threshold 5, 400 for an
out-of-range threshold (propose the range). Plan in slices, each with its test and the files it touches.
After approval, your only step is to write this plan into ai-session/PLAN.md with the sections
Approved by, Goal, Slices (checkboxes), Decisions made by the human (keep what is there) and
Changes to this plan. Then stop. No code.
  3. Approve with your hands on the wheel. When the plan appears, choose Yes, manually approve edits. Accept the edit to ai-session/PLAN.md; answer no to any other file. Then git status should list only that file.
  4. Red pen. Open ai-session/PLAN.md in your editor and make at least one real change: split a slice, add a missing test, fix the range (for example 0 to 1000, with a test that 1001 returns 400), or strike something the brief doesn't ask for. Note what you changed and why. Fill in Approved by.
  5. Commit the plan alone. 
    git add ai-session/PLAN.md
git commit -m "docs(plan): low-stock endpoint"
git show --stat HEAD
    The stat lists one file.
  6. Scope bait. Say: "While you're at it, add an API-key check so only staff can call this." Expect a refusal that cites your out-of-scope rule (AGENTS.md or docs/ai/invariants.md). If it complies, refuse the edits and strengthen that line in AGENTS.md.
  7. One slice. Prompt "Implement only the first unchecked slice in ai-session/PLAN.md, with its test. Stop when it is done." Run dotnet test yourself and read git diff. Tick the slice, then stage the slice's files by name (git status shows new files too) plus the plan: 
    git add src/StockApi/Controllers/ProductsController.cs
git add tests/StockApi.Tests/<your test file> ai-session/PLAN.md
git commit -m "feat(products): low-stock endpoint"
    If your plan has more low-stock slices, build each the same way.
  8. The change. Paste this in as if a colleague had sent it: "Low-stock must also accept an optional skuPrefix filter." The right response is to update the plan, not code: refuse any code edit. Check the new slice has a test and a line under "Changes to this plan" with the reason. Approve it, then commit it alone: 
    git add ai-session/PLAN.md
git commit -m "docs(plan): add skuPrefix filter"
  9. The new slice. Implement only that slice, run dotnet test, read the diff, tick it, stage its files plus ai-session/PLAN.md by name, and commit feat(products): skuPrefix filter.
  10. Run git log --oneline. Each plan commit sits directly before the code it governs.

Codex: plan with sandbox_mode set to read-only and "plan only, no edits", then switch back for the slices. Antigravity: use /plan, then copy the approved plan into ai-session/PLAN.md. The commits are the same.

Done when: tick all four to earn the Plan Gatekeeper plaque
  • git show --stat on docs(plan): low-stock endpoint lists only ai-session/PLAN.md, and it comes before the first feat(products) commit
  • Approved by is filled in, and you can name one thing you changed in the agent's draft
  • docs(plan): add skuPrefix filter comes before the skuPrefix feature commit
  • dotnet test is green and both slices are ticked in PLAN.md
