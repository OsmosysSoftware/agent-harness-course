Code and docs written for the agent as reader

The most frequent reader of your code and docs is now the agent. It doesn't skim and it forgets, and it "fixes" anything that looks odd. Write for that reader: constraints not narratives, decisions recorded with their reason, rules enforced by tests, and docs audited against the code.

The win

What the harness does instead

The docs are instructions for the next agent: short, one topic per file, loaded when relevant. The odd-looking decision (one guarded UPDATE) has an ADR that says it's intentional and why. The claim "safe under concurrency" is a test that places 12 orders for 3 units and fails otherwise, not a sentence in a README.

A skill, update-docs, compares every claim with the code. It would have caught Trainee C's line; the review says so.

Going deeper: when you do need a CLAUDE.md

Claude Code reads AGENTS.md natively from v2.1.277, but only when no CLAUDE.md exists. Before v2.1.281, some sessions (for example Amazon Bedrock, or telemetry disabled) read CLAUDE.md only. If you meet one of those, add a one-line CLAUDE.md containing @AGENTS.md. It is the fallback, never a second copy of the rules.

The size target comes from Anthropic: "target under 200 lines per CLAUDE.md file", and imports "don't reduce its context cost, because imported files also load at launch" (Memory). Lesson 2's test for each line still applies: would removing this cause the agent to make a mistake?

Record the decision: the ADR

An ADR (architecture decision record) is a short file that records one decision: context, what was decided, consequences. Humans write them so the next person doesn't undo the decision without knowing why. An agent has the same problem, worse: to a model, anything unusual is a candidate for "cleanup". The ADR is what makes the oddity intentional on the page. It is the reference solution's file, verbatim:

Read the middle paragraph of Context twice, because it's the lesson inside the lesson. We measured it: on SQLite, read-then-write inside a transaction passes the concurrency test, because Microsoft.Data.Sqlite (the EF Core provider, the plug-in that talks to one particular database) takes the write lock up front. So a green guard test can be green for the wrong reason: the provider's locking, not your design, was holding the invariant. Trainee D's code oversold on SQL Server (READ COMMITTED); it would also oversell here the moment the transaction went away, which is what an InMemory-driven rewrite does. That's why the ADR's Consequences section assigns the last word to a reviewer that reads the code, not only to a test that runs it. Tests and reviewers cover different failures; you need both.

The ADR is referenced from three places so an agent finds it whichever path it takes: docs/ai/invariants.md ("Why: docs/decisions/0001-…"), .claude/rules/efcore.md, and a one-line comment at the code. Right now OrderService.cs line 17 has a dangling pointer, "// Atomic guarded UPDATE: no read-then-write. See docs/decisions (added in lesson 9)."; the exercise replaces that whole comment with // Atomic guarded UPDATE, never read-then-write: see docs/decisions/0001. It also adds the other two pointers.

Check yourself

An agent rewrites the stock update to tracked entities, but ConcurrencyTests stays green on SQLite. Why must the change still be blocked?

Microsoft.Data.Sqlite takes the write lock when the transaction starts, so read-then-write inside one passes. Remove the transaction, or move to SQL Server, and it oversells. The ADR says the test can't see that; the reviewer can.

Trainee C's doc said "JWT rejected"; JWT was committed a minute later. Which practice catches this?

update-docs requires evidence for every claim (file:line, commit or test) and labels the rest STALE or UNVERIFIABLE. "Rejected" would have had no matching event.

From the agent's side, what is an ADR mainly for?

An agent "corrects" anything that looks unusual. The ADR states the choice, the reason and what breaks if it's undone, so the model leaves it alone or hands over a 1-3-1.

Exercise: make the repo readable, then test the ADR

Exercise · ~40 min · adds: ADR, conventions.md, two skills, pointer comments
  1. Write the ADR and conventions. Create docs/decisions/0001-atomic-guarded-update.md and docs/ai/conventions.md from the listings above. Ask the agent to draft them if you like, but read every line, and change anything your repo doesn't match (for example your low-stock endpoint). Link both from AGENTS.md under "More context". One line in conventions.md needs a file your practice repo doesn't have yet: "warnings are errors (Directory.Build.props)". Recommended: make it true. Copy Directory.Build.props from reference-solution/ to your repo root (it is six lines: nullable, implicit usings and TreatWarningsAsErrors), run dotnet build -warnaserror to confirm it is still clean, and commit it with the docs. The capstone relies on it. The alternative is to delete that bullet, but then your docs and your build disagree with the reference.
  2. Add the two skills in the tool-neutral place, then link each for Claude Code. Windows: run these in WSL2 or Git Bash (see Before you start on the index). 
    mkdir -p .agents/skills/new-endpoint .agents/skills/update-docs
# write both SKILL.md files, then:
ln -s ../../.agents/skills/new-endpoint .claude/skills/new-endpoint
ln -s ../../.agents/skills/update-docs  .claude/skills/update-docs
ls -l .claude/skills
    ls -l should show new-endpoint -> ../../.agents/skills/new-endpoint. The link's target is relative to the link's own folder (.claude/skills/), not to where your shell is, which is why it starts with ../... If the arrow points at a path that doesn't exist, delete the link with rm .claude/skills/new-endpoint and redo it.
  3. Adapt the skill to your repo. new-endpoint names tests/StockApi.Tests/ProductsTests.cs as the reference shape, but your practice repo has only tests/StockApi.Tests/ApiTests.cs. Easiest: edit the two reference-shape paths in new-endpoint/SKILL.md to point at ApiTests.cs. (Splitting the product tests into ProductsTests.cs also works, but is extra work for no gain today.) Otherwise the skill sends the agent to a file that doesn't exist.
  4. Point the code at the ADR. In OrderService.cs, replace the dangling comment on line 17, // Atomic guarded UPDATE: no read-then-write. See docs/decisions (added in lesson 9)., with // Atomic guarded UPDATE, never read-then-write: see docs/decisions/0001. One line, no essay.
  5. Add the other two pointers. In docs/ai/invariants.md, under invariant 1, add the line - Why: docs/decisions/0001-atomic-guarded-update.md. In .claude/rules/efcore.md, make sure the stock-changes line ends with (docs/decisions/0001). Then open your stock-invariant-reviewer agent file: lesson 6 told you its ADR reference would resolve only after this lesson, so confirm it now says "Read docs/ai/invariants.md and docs/decisions/0001-atomic-guarded-update.md first" (use your own reviewer's name if it differs). Add that sentence if you left it out. Without these, the ADR test in step 7 can pass or fail for the wrong reason.
  6. Run the audit. /update-docs. Expect at least one STALE row: README.md lists the endpoints as they were before lessons 4 and 8. (If the skill isn't found, start a new session so it loads; the sample table above shows the shape of a good answer.) Now plant two false claims yourself, in the style of Trainee D: in AGENTS.md write "Stock writes use row locking (SELECT … FOR UPDATE)", and in README.md change the run command to dotnet run --project src/Api. Run /update-docs again. Both must come back STALE with evidence. Approve the proposed diff, confirm the false claims are gone, and do not keep any you planted.
  7. The ADR test. Start a new session. Ask: "Simplify OrderService.PlaceAsync: load the product, check Stock, decrement and SaveChanges. It is shorter." Pass: it cites docs/decisions/0001 (or invariants.md), declines or hands over a 1-3-1, and doesn't edit. Fail: it edits. If it edits, run stock-invariant-reviewer on the diff and expect BLOCK, then improve the ADR or the invariant line and re-run in another new session.
  8. Optional, to see the test turn red. On a scratch branch: make the rewrite yourself (load, check, decrement, SaveChanges) and remove the transaction. ConcurrencyTests fails (measured on the reference solution: "Expected: 3 / Actual: 12"). Put the transaction back and it passes again, which is the "green for the wrong reason" case from the ADR. Discard the branch.
  9. Commit through /commit: docs: add ADR 0001 and conventions (include Directory.Build.props and the two pointer lines), then chore(harness): add new-endpoint and update-docs skills.
