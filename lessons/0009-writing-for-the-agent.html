Code and docs written for the agent as reader

The reader your repo has most often is now an agent. It starts every session cold, can't ask the author, takes every sentence at face value, and treats anything unusual as a candidate for cleanup. Write for that reader: the reason next to the odd choice, one shape to copy, and docs checked against the code.

12 min read 45 min exercise Plaque: Agent's Author
In 30 seconds
  • Code that looks odd on purpose needs its reason written down, in an ADR, and a one-line comment that points to it.
  • Agents imitate well, so give them one reference shape to copy, and make every convention match it.
  • Docs drift. A skill, /update-docs, checks each claim against a file:line, a commit or a test, and marks it TRUE, STALE or UNVERIFIABLE.

What happened

Failed run

A developer's project kept a document of decisions. One line said JWT authentication was "rejected, not requested". One minute after that line was committed, JWT was committed. Nothing checked the document against the code.

In another session, the tests couldn't run the atomic stock update, so the agent rewrote it as read-then-write and called it "still correct against concurrent writes". Nothing in the repo said why the original looked the way it did. A live test of 12 concurrent orders for 3 units oversold.

With the harness

The odd-looking update carries one comment line, // … see docs/decisions/0001, and that file says what breaks if it is "simplified". A skill checks every doc claim for evidence:

The reader changed

Lesson 1: the agent knows only what is in its context window. Every new session starts empty and fills it from your repo: the rules file, then whatever it opens. A human colleague who finds odd code asks around. The agent asks nobody: what is on the page is all it has. So the question for this lesson is what the page should say. One habit you already have: where a rule can be a test, make it one. ConcurrencyTests (lesson 7) fails when stock oversells, however convincing the prose around it.

Record the decision: an ADR

An ADR (architecture decision record) "captures a single AD [architectural decision] and its rationale" (adr.github.io): a short Markdown file with the context, the decision and its consequences. Teams write them so the next person doesn't undo a decision without knowing why. An agent needs that more than a person does. Watch what one does with your stock update:

Here is the ADR you will write. It is short on purpose: what was decided, why, and what breaks if someone undoes it.

No tool loads docs/decisions/ by itself, so an ADR nobody points to is never read. Point to it from wherever the agent will be when it matters: a one-line comment at the code, a Why: line in docs/ai/invariants.md, the stock reviewer's first instruction, and a "More context" line in AGENTS.md. Keep the comment to one line. The reasoning lives in one file, so it can't go stale in five.

Your AGENTS.md already forbids read-then-write, so a fresh session may decline even without the ADR. What the ADR adds is the why, which keeps the rule standing when someone argues "it is shorter", and a way to change the decision on purpose.

One shape to copy

Agents are good at imitation. "Copy the shape of ProductsController and its tests" works better than a page of description, and the new-endpoint skill says exactly that. docs/ai/conventions.md lists the rules around the shape, each one checkable against the code:

The conventions must match the shape. An early draft said "controllers are HTTP only" and "never return entities", while ProductsController uses the DbContext and returns Product. An agent given both picks one, and you can't predict which. The fix is to describe what the reference really does.

One line names a file your practice repo doesn't have: Directory.Build.props. You will add it rather than drop the line. Your quality gate already builds with -warnaserror, so the file changes nothing the gate checks, and a plain dotnet build now agrees with it.

Going deeper: the two skills in full

Neither skill restates the conventions; each points at them, so there is one place to edit. The course's reference solution keeps the first draft of new-endpoint (the one that names ProductsTests.cs and forbids returning entities), so write yours from this listing rather than copying it.

Docs drift: check claims against the code

Docs are written once and the code keeps moving. Your README.md still lists the four endpoints the starter had; lessons 4 and 8 added two more. A doc that is wrong is worse for an agent than no doc, because the agent believes it. update-docs makes the check a procedure:

Three choices make it work. Every verdict needs evidence, so the skill can't approve a claim just by agreeing with it. It proposes edits and waits, because changing shared docs is your call. And it forbids narrative: a docs folder is instructions for the next agent, not a story about the last one. On a trial run against a copy of the exercise repo it found the README endpoints and several more drifted claims, including a line in invariants.md that names a .env.example the repo doesn't have.

Check yourself

You add // … see docs/decisions/0001 above the stock update. What does it buy you?

The comment sends the agent to the reason before it edits, so it is more likely to decline and cite 0001. Nothing loads the ADR automatically and nothing guarantees obedience, which is why the reviewer and ConcurrencyTests stay.

/update-docs finds the README lists 4 endpoints and the code has 6. What should it do?

STALE with evidence (the controller lines), a proposed diff, and no edit until you approve. The code is the truth here; the doc moves to match it.

A doc says "we carefully considered SQL Server", and nothing in the repo mentions it. The verdict?

No evidence either way, so it is neither TRUE nor STALE. The honest fix is usually to delete the sentence: it tells the next agent nothing it can act on.

Exercise: give the odd code its reason, then test it

Exercise · about 45 min · you add: an ADR, conventions.md, Directory.Build.props, two skills, pointers to the ADR

Work in your practice repo (~/projects/stockapi), with this course's repo cloned beside it. After lessons 1 to 8 it has AGENTS.md, docs/ai/, a plan, the commit and quality-gate skills, two reviewers, guards and ConcurrencyTests. Windows: use WSL2 or Git Bash (setup).

  1. Start clean. git status should say nothing to commit, working tree clean, on main.
  2. Write the ADR. Run mkdir -p docs/decisions, then create docs/decisions/0001-atomic-guarded-update.md from the listing above, with today's date. Read every line: if your repo differs (a different status code, say), the ADR must say what your code does.
  3. Point at it, four times.
    • In src/StockApi/Services/OrderService.cs, replace // Atomic guarded UPDATE: no read-then-write. See docs/decisions (added in lesson 9). with // Atomic guarded UPDATE, never read-then-write: see docs/decisions/0001.
    • In docs/ai/invariants.md, add a last bullet to invariant 1: - Why: docs/decisions/0001-atomic-guarded-update.md (lesson 2 had you delete it).
    • In .claude/agents/stock-invariant-reviewer.md, change "Read docs/ai/invariants.md first." to "Read docs/ai/invariants.md and docs/decisions/0001-atomic-guarded-update.md first." (lesson 6 left it out).
    • Under "More context" in AGENTS.md, add - Code layout, errors, the shape to copy: docs/ai/conventions.md and - Deliberate decisions, with the why: docs/decisions/.
    Then check: 
    grep -rn "decisions/0001" src docs/ai .claude/agents
grep -rn "added in lesson 9" src
    Expect three lines from the first (the comment, the Why: line, the reviewer) and nothing from the second.
  4. Conventions, and the file they name. Create docs/ai/conventions.md from the listing above. Check each line against your code, for example grep -rn DateTimeOffsetToBinaryConverter src should find lesson 8's converter. Then make the warnings line true: 
    cp ../agent-harness-course/reference-solution/Directory.Build.props .
cat Directory.Build.props        # Nullable, ImplicitUsings, TreatWarningsAsErrors
    Run /quality-gate: expect quality gate: green.
  5. Add the two skills. Write both SKILL.md files from "Going deeper: the two skills in full"; new-endpoint names ProductsTests.cs; change both mentions to ApiTests.cs, the test file your repo has. Then link them as in lesson 5: 
    mkdir -p .agents/skills/new-endpoint .agents/skills/update-docs
# write .agents/skills/new-endpoint/SKILL.md and .agents/skills/update-docs/SKILL.md, then:
ln -s ../../.agents/skills/new-endpoint .claude/skills/new-endpoint
ln -s ../../.agents/skills/update-docs .claude/skills/update-docs
ls -l .claude/skills
    Four lines with ->. (Git Bash without Developer Mode: copy the folders instead, as in lesson 5.)
  6. Commit, twice, through /commit. First the docs and the code comment: docs: add ADR 0001, conventions and pointers (the ADR, conventions.md, invariants.md, AGENTS.md, the reviewer, OrderService.cs, Directory.Build.props). Then feat(harness): add new-endpoint and update-docs skills.
  7. Run the audit. Start a fresh session (claude --permission-mode default) and type /update-docs. Expect a table, and at least one STALE row: README.md is missing GET /api/products/low-stock and GET /api/orders. It may flag more, such as the .env.example line in invariants.md. For each STALE row, open the evidence it cites and decide yourself.
  8. Fix what is stale. Approve the README change and any other row you checked and agree with; say no to the rest, with a reason. Run /update-docs again: the README rows should now be TRUE. Commit through /commit: docs: fix stale README endpoints.
  9. Test the ADR. Start a new session in Manual mode (claude --permission-mode default) and ask: "Simplify OrderService.PlaceAsync: load the product, check Stock, decrement and SaveChanges. It is shorter." Pass: it cites docs/decisions/0001 (or invariants.md), declines or hands you options, and edits nothing; git status stays clean. If it proposes an edit, answer No: the ADR didn't hold this time. Sharpen its Consequences and the Why: line, then try again in another new session. Any edit that does land still meets the stock reviewer and ConcurrencyTests.

Codex: skip the symlinks; it reads .agents/skills/ directly, so type $update-docs, and ask the reviewer by name. Antigravity: the same folder works; type /update-docs, and start a new conversation for the ADR test.

Done when: tick all four to earn the Agent's Author plaque
  • docs/decisions/0001-…md is committed, and grep -rn "decisions/0001" src docs/ai .claude/agents finds the comment, the Why: line and the reviewer
  • docs/ai/conventions.md and Directory.Build.props are committed, and /quality-gate is green
  • ls -l .claude/skills shows four links, and /update-docs flagged the README endpoints as STALE before your fix
  • A fresh session asked to simplify OrderService cited the ADR or the invariants and edited nothing
