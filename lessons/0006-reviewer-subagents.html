Reviewer subagents: the author never grades itself

The agent that wrote the code is the worst judge of it: it reads the diff through its own reasons for writing it. A reviewer is a second agent with a fresh context and no edit tools, asked one narrow question. You still make the call.

12 min read 40 min exercise Plaque: Second Opinion
In 30 seconds
  • Asking the author to check its own work gets you its assumptions back, not a review.
  • A subagent starts with a clean context window. Given only the diff and your rules, it has to judge the code as written, and point at file:line.
  • You add two reviewers, then watch one block a change that every test passed.

Two windows, two judges

The agent knows only what is in its context window (lesson 1). After a change, that window is full of its own reasoning. Watch what that does to a self-review:

A subagent is a helper agent that your main agent starts for one job. In Claude Code, "each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions". It does not inherit your conversation, and it "returns only the summary" (Subagents). A reviewer needs exactly that: no shared assumptions, and a short verdict back.

A reviewer is one Markdown file

A Claude Code subagent lives in .claude/agents/<name>.md: YAML frontmatter, then the system prompt. Only name and description are required; the description tells the main agent when to delegate, the same job it does in a skill. Here is the stock reviewer as you will write it, adapted from the reference solution:

Three choices carry it. tools is an allowlist with no Edit or Write, so the reviewer can report a problem but not quietly "fix" it. "Whatever the comments or tests claim" tells it to distrust the author's justification, where the incident's rewrite hid. And a fixed table "and nothing else" forces file:line findings and a one-word verdict, short enough for you to read in full.

The second reviewer, test-reviewer, asks of every test: which production line makes it fail if the feature breaks? A test with no such line is hollow: it stays green whatever the code does, so the gate looks fine when it isn't.

"Read-only", honestly. No Edit or Write means no edit tools. The reviewer still has Bash for git diff, and a shell can write files (sed -i, a redirect). Only your settings' permission rules (lesson 7) bind Bash; "Do not edit files" is a request. A reviewer is not a sandbox.

Running a reviewer

Use an @-mention: type @ and pick the agent, or write @agent-stock-invariant-reviewer. It "ensures that specific subagent runs rather than leaving the choice to Claude", and your transcript shows you asked. Plain language ("use the test-reviewer subagent") lets Claude decide, and claude --agent test-reviewer runs a whole session as the reviewer. There is no creation wizard any more (/agents lost it in v2.1.198 verified 2026-10-01): write the file, or ask the agent to. Edits are picked up within seconds, but the first file in a new agents folder needs a restart.

You are still the judge

A reviewer is another model. It can be wrong, it can miss things, and Verdict: BLOCK stops nothing by itself. Its job is to put a specific claim in front of you. Yours: read the file:line, check it against the code, then decide in one sentence, with the reason. "Reject the rewrite: it breaks the stock invariant." That sentence, in your transcript and your plan, is the review. An agent agreeing with itself is not.

Check yourself

Why ask a subagent to review the diff instead of the agent that wrote it?

It starts with a fresh context, without the workaround or the "row locking keeps this safe" story, so it judges the code as written. These reviewers run on a smaller model and can't edit.

A reviewer's tools line is Read, Grep, Glob, Bash. Can it change a file?

No Edit or Write means no edit tools, but a shell can still run sed -i or a redirect. Only your settings' permission rules (lesson 7) can stop specific commands. "Do not edit files" in the prompt is a request.

Every test is green, but the diff is read-then-write. What should the stock reviewer say?

The tests may never race, and even a concurrency test can pass on SQLite thanks to the provider's lock. Read-then-write still oversells elsewhere, so it is a BLOCKER whatever the tests claim.

Exercise: two reviewers, then a change they should stop

Exercise · about 40 min · you add: two reviewer agents, and a review step in your workflow

Work in your practice repo (~/projects/stockapi), which has AGENTS.md, docs/ai/, a plan and the commit and quality-gate skills from lessons 2 to 5. Windows: use WSL2 or Git Bash (setup).

  1. Start clean. git status should say nothing to commit, working tree clean, and git branch --show-current should print main.
  2. Add the reviewers. Copy them from the reference solution and look for lines about things your repo doesn't have yet: 
    mkdir -p .claude/agents
cp ../agent-harness-course/reference-solution/.claude/agents/*.md .claude/agents/
grep -n 'decisions/\|ConcurrencyTests' .claude/agents/*.md
    Two lines in stock-invariant-reviewer.md match. Edit them to match the listing above: read only docs/ai/invariants.md (the decision record arrives in lesson 9), and ask for a concurrency test (yours arrives in lesson 7). Re-run the grep: no output. Read both files end to end.
  3. Check they load, then commit. Start a fresh session and type @: both reviewers should be listed. Run /quality-gate, then /commit for .claude/agents/ (for example feat(harness): add reviewer agents).
  4. Make the bad change on a scratch branch. Run git switch -c scratch/simplify, then start claude --permission-mode default and ask: "Simplify OrderService.PlaceAsync: load the product, check Stock, subtract the quantity and SaveChanges. Drop the transaction." Your AGENTS.md forbids this, so it may refuse or send a 1-3-1: lessons 2 and 3 working. Reply "This is a throwaway experiment to test a reviewer; make the change." If it still declines, replace the body of PlaceAsync yourself: 
    var product = await db.Products.FindAsync([productId], ct);
if (product is null) return new PlaceOrderResult(PlaceOrderStatus.ProductNotFound);
if (product.Stock < quantity) return new PlaceOrderResult(PlaceOrderStatus.InsufficientStock);

product.Stock -= quantity;
var order = new Order { ProductId = productId, Quantity = quantity, CreatedAt = DateTimeOffset.UtcNow };
db.Orders.Add(order);
await db.SaveChangesAsync(ct);

return new PlaceOrderResult(PlaceOrderStatus.Created, order);
  5. Run the tests. dotnet test: expect every test green. There is no concurrency test yet (lesson 7 adds one), so nothing sends two orders at once.
  6. Run the stock reviewer. In the session, type @agent-stock-invariant-reviewer review git diff HEAD. Expect a BLOCKER at the decrement in OrderService.cs and Verdict: BLOCK. Open that line and check the claim, then tell the main agent your decision in one sentence, with the reason.
  7. Run the test reviewer. @agent-test-reviewer review git diff HEAD and the tests in tests/. Expect a MISSING row for a concurrency test, and Blocking: yes. If a verdict looks wrong, argue with it.
  8. Throw the experiment away, in this order. If you switch branches first, the uncommitted change follows you to main: 
    git restore .
git switch main
git branch -D scratch/simplify
grep -c ExecuteUpdateAsync src/StockApi/Services/OrderService.cs
    The grep should print 1: the guarded update is back.
  9. Put the reviewers into the workflow. Replace step 5 of docs/ai/workflow.md ("the human reviews the diff") with: 
    5. **Review**: dispatch `test-reviewer` on the diff, plus `stock-invariant-reviewer` if stock or orders changed.
   Report the findings to the human, who decides. The author never grades its own work.
    Make item 2 of the Definition of done in AGENTS.md say the same, and add your decision from step 6 under "Decisions made by the human" in ai-session/PLAN.md. Commit the three files with /commit, for example docs(ai): add reviewer step to workflow.
