Reviewer subagents: the author never grades itself

A reviewer is a second agent with a fresh context and read-only tools, asked one narrow question about a diff. The agent that wrote the code is the worst judge of it, and you are the final one.

Recall

A CLAUDE.md file sits in the repo next to AGENTS.md. What does Claude Code read?

Claude Code falls back to AGENTS.md only when no CLAUDE.md exists. The usual fix is a CLAUDE.md that contains @AGENTS.md (lesson 2).

Why is the plan committed on its own, before any code?

Trainee D's PLAN.md arrived inside the commit that held the whole API, so nothing could show it was written first. A plan committed alone, with the human's edits, is evidence (lesson 4).

The win

By the end you'll have two reviewer agents in .claude/agents/. You'll have watched stock-invariant-reviewer return Verdict: BLOCK on a "simplified" OrderService that the agent was happy with, and test-reviewer flag a missing concurrency test.

What happened

What happened

Trainee B's repo shows a "review round that found eight real defects". The evaluator scored it 5 for critical review of AI output. It was the agent running a review skill over its own diff. No transcript shows them asking for the review or judging the findings.

Trainee A pasted a 9-point "critically review your code" checklist into the prompt, and the same agent reviewed its own work. Two misleading tests got through until they caught them themselves.

Trainee B · Claude Code, "Chat" stage, self-review · Trainee A · Claude Code, "Gated chat" stage, human-led

What the harness does instead

The review runs in a separate agent with a fresh context. It has never seen the conversation that produced the diff, so it can't share the author's assumptions. It gets only the diff and a narrow question, and it reports to you. Whether the code goes in is your call, and the transcript shows it.

What happened

Trainee D's agent hit ExecuteUpdateAsync … could not be translated (InMemory provider). It rewrote the order service to load tracked Product entities, decrement in memory and save. Its log justified this: "still correct against concurrent writes, because SQL Server's row locking … serializes two orders".

That justification was false. The evaluator's live probe, 12 concurrent orders for 3 units, oversold. The rewrite sat inside commit 1009656, a 67-file commit, where no one could review it alone.

Trainee D · Claude Code · Sonnet · "Chat" stage: every catch was the agent's, and they accepted a racy rewrite

What the harness does instead

A stock-invariant-reviewer reads every diff that touches stock or orders, and treats read-then-write as a BLOCKER "whatever the comments or tests claim". The author's own explanation ("row locking makes it safe") is exactly what it is told not to accept.

Why a fresh context beats a checklist

A subagent is an agent that the main agent starts to do one job. In Claude Code it "runs in its own context window with a custom system prompt, specific tool access, and independent permissions", and it starts fresh: it does not inherit the conversation (Subagents). Two properties follow:

  1. No shared assumptions. The author "knows" why it chose read-then-write, and every later message builds on that. A reviewer that sees only the diff and the rules has to judge the code as written. Trainee A's 9-point checklist failed for this reason: a checklist in the author's own context is read by the author.
  2. A small, cheap context. The reviewer's reading (diff, invariants, tests) stays in its window, and only the findings come back to yours.

The anatomy of a reviewer file

A Claude Code subagent is a Markdown file in .claude/agents/<name>.md: frontmatter, then the system prompt. name and description are required. The description is how the main agent decides when to delegate to it, the same role as in a skill (frontmatter fields).

Read-only, honestly

Leaving out Edit and Write makes the reviewer read-only in practice, not in principle. It still has Bash, because it needs git diff. Bash is still bound by the project's permission rules: the docs say project deny rules apply to subagents too, so the deny and ask rules in .claude/settings.json (lesson 7) cover the commands they name, such as git push. None of them forbids sed -i or a redirect, and a shell can write a file (sed -i, a redirect) unless a rule stops that. "Do not edit files" in the agent body is a request. disallowedTools can't narrow this, because "an entry with a specifier, such as Bash(git push *), still removes the whole tool". So: no edit tools, plus the settings rules, plus a reviewer prompt that says not to, and all three are still not a sandbox. Codex offers a real one, below.

How to invoke one

There are three ways, from loosest to strictest (Invoke subagents explicitly):

  • Natural language: "Use the test-reviewer subagent on the staged diff." Claude decides whether to delegate.
  • @-mention: type @ and pick the agent, or write @agent-test-reviewer. This "guarantees the subagent runs for one task". Use it when you want certainty, and in the exercise.
  • --agent <name>: the whole session becomes that agent, with its tool limits. Good for a dedicated review session.

The two reviewers, verbatim

The core question is item 1 of the procedure: "what line fails if the feature breaks?" For each test, the reviewer must name the exact file:line whose removal or inversion makes the test fail. A test that has no such line is hollow: it can pass forever whatever the production code does (it asserts "no exception", or asserts on a value the test itself set). Trainee A's two misleading tests got through because nothing asked that question. A hollow test is worse than none, because the gate goes green. Note the last rule of the body: "Do not praise". A reviewer that opens with compliments is producing the tone of a chat, not a verdict.

This one guards one invariant, and only runs on diffs that touch stock, orders, OrderService, StockDbContext or transactions. (In your copy, drop "and docs/decisions/0001-atomic-guarded-update.md" from the first paragraph until lesson 9 creates that file.) Two lines carry the lesson:

  • "whatever the comments or tests claim." The reviewer is told to distrust the author's justification, which is where Trainee D's rewrite hid.
  • Item 5 asks whether the diff changed a test provider or helper "in a way that hides a concurrency failure". That's the InMemory swap itself.

A green test can be green for the wrong reason

We measured this on the reference solution. Read-then-write inside BeginTransactionAsync() passes the 12-for-3 concurrency test on SQLite, because Microsoft.Data.Sqlite starts a non-deferred transaction that takes the write lock up front (Microsoft docs). It fails (Expected: 3 / Actual: 12) only when the transaction is removed too, which is what an InMemory-driven rewrite does, since InMemory rejects transactions. On SQL Server at READ COMMITTED it oversells, as Trainee D's did. So the test passing tells you about the provider's locking, not about the design. That's why the reviewer blocks read-then-write even when the suite is green, and why docs/ai/invariants.md says it "only looks safe inside BeginTransaction()". A guard test and a reviewer cover different failures, and lesson 7 adds the test.

The human is still the final judge

A reviewer is another model. It can be wrong, it can miss things, and Verdict: BLOCK doesn't stop a commit by itself. The workflow in docs/ai/workflow.md says it in one line: "Report its findings to the human. The author never grades its own work." So:

  1. You trigger the review (an @-mention is the clearest trace), or the Definition of done in AGENTS.md does.
  2. The findings come back to you, unedited by the author agent.
  3. You decide: fix it, reject the finding with a reason, or ask the author to explain. Write that decision in the chat.

This matters for how you'll be assessed. Credit for critical review of AI output needs "a human prompt that triggered the review, or a human rejection or change, visible in the transcript". The agent reviewing itself, even through a review skill, is "agent work — note it, do not credit it as human review". Trainee B's "eight defects" were not credited as human review, because the human's decision wasn't visible. The assessment caps the score for critical review at 3 when the only review is the agent's own.

Check yourself

When does the test reviewer call a test hollow?

The core question is "what line fails if the feature breaks?" If the reviewer cannot name one, the test would stay green whatever the code does. A naming slip is only a style note.

The reviewer has no Edit or Write tool. Can it still change files?

Without Edit and Write the reviewer has no edit tool, but Bash can still run sed -i or a redirect. The prompt asks it not to, and settings rules cover only the commands they name. "Read-only" here is a strong request, not a sandbox; a real guarantee needs one (Codex offers it).

The concurrency test is green, but the diff is read-then-write. What should the reviewer do?

On SQLite, read-then-write inside a transaction can pass the test because of the provider's write lock. The design still oversells without the transaction or on another database, so it is a BLOCKER whatever the tests claim.

Your repo now has AGENTS.md, the plan workflow, and the commit and quality-gate skills. Commit every step below through /commit.

and "Blocking: yes/no". stock-invariant-reviewer: block any read-then-write stock

Tools: Read, Grep, Glob, Bash only. Model: sonnet. They must not edit files.
    The stock reviewer reads docs/ai/invariants.md, which you wrote in lesson 2. In your copy, leave out the sentence that names docs/decisions/0001-atomic-guarded-update.md (and any "Why: docs/decisions/0001…" line in your invariants.md): that decision record doesn't exist until lesson 9 adds it, and a reviewer told to read a missing file wastes its first move.
  2. Start a new session, then run /quality-gate and /commit for the two files (feat(harness): add reviewer agents).
  3. Point the workflow at the reviewers. Step 5 of docs/ai/workflow.md is still a manual placeholder. Edit it to say: dispatch test-reviewer on every diff, and stock-invariant-reviewer as well when stock or orders change; report the findings to the human; the author never grades its own work. Make item 2 of the Definition of done in AGENTS.md say the same. Commit both through /commit: docs(ai): point workflow at reviewers.
  4. Try the trap on a scratch branch. Run git switch -c scratch/simplify. Ask the agent: "Simplify OrderService.PlaceAsync: load the product, check Stock, decrement it and SaveChanges." Let it edit. Then remove the transaction if it kept one, which is what an InMemory-driven rewrite does. Run dotnet test and note the result: expect every test green, because your repo has no concurrency test yet (lesson 7 adds one). Hold on to that: green tests are exactly why the agent thought the rewrite was fine.
  5. Run the stock reviewer with an @-mention so you know it ran: @agent-stock-invariant-reviewer review git diff HEAD. Expect a table with a BLOCKER on the read-then-write and Verdict: BLOCK. Now say to the main agent, in your own words, what you decide (for example "Reject the rewrite, keep the guarded update"). That sentence is your evidence of critical review.
  6. Run @agent-test-reviewer review the tests. Expect it to flag that no test covers concurrent orders (lesson 7 adds one). Read how it names the production line for each existing test; if a verdict looks wrong, argue with it.
  7. Discard the experiment: git restore . then git switch main and git branch -D scratch/simplify. You need no commit for discarded work.
  8. Optional: start a dedicated review session with claude --agent test-reviewer and compare how the same diff looks there.
