Capstone: harness in 30 minutes, then the swap test

You'll build the harness on a brand-new repo against a timer, before any feature code, then hand the repo to a fresh agent session and a partner who says nothing. A harness that only works for the person who wrote it isn't one. This is the next assessment, rehearsed.

Lesson 8: a server is a program started on your machine, so the prompt is the one checkpoint before a teammate's .mcp.json runs as you.

The win

By the end you'll have committed a harness to a repo you'd never seen, before any feature code: first untimed (expect 60 to 90 minutes), then again against a 30-minute timer once you have a template. You'll also have a scored swap test, on two repos, that shows where your harness steers a fresh agent and where it doesn't. Every gap becomes a committed fix.

What the harness does instead

The format enforces order: the harness is checked at 0:30, "before feature code exists". Then the evaluator runs a swap test: a fresh agent session, in a fresh clone, with no extra instructions, on a task the candidate never prompted. The measure is whether your files steer an agent that has never seen your chat.

"A great prompt may be written by another AI" stops mattering: "Irrelevant if the harness works in the swap test."

Decide on the output style, deliberately

The Learning output style (lesson 1) leaves TODO(human) markers and pauses for you at design decisions. That is wonderful for learning and costly against a 30-minute clock, since every pause is minutes. It's a personal setting saved in .claude/settings.local.json, so it won't reach a fresh clone. Choose before you start: /output-style default for the timed build, or keep Learning and accept the pauses. Don't discover the choice at minute 20.

The one piece you write new: the overlap invariant

Your new reviewer guards the brief's invariant the way stock-invariant-reviewer guards stock. The shape to copy: name the invariant, name the forbidden pattern, name the guard test, and output a verdict. The forbidden pattern is the same idea as lesson 9's read-then-write: query for an overlapping booking, find none, then insert. Two requests in flight both find none. Two intervals overlap when a.Start < b.End && b.Start < a.End. The safe form makes the check and the insert one statement (sketch):

Two decisions in there are the human's, which makes them good 1-3-1 material: whether a booking that ends at 10:00 and one that starts at 10:00 overlap (the brief doesn't say), and what a reschedule should do about its own old window. The brief stores times as UTC DateTime, which is one of the two fixes Microsoft lists for SQLite's DateTimeOffset limit (lesson 8), so that trap is already avoided.

The swap test

The evaluator's steps, quoted from the design notes:

You'll run it twice, once per repo, on these tasks. The practice repo: "Add PATCH /api/orders/{id}/cancel that returns stock." RoomBooking: "Add PATCH /api/bookings/{id}/reschedule." Each touches the invariant (a cancel must return stock once, even on a double cancel; a reschedule must not overlap another booking, and must not collide with itself), and each has real decisions to hand over. Adding a column to Orders is one: EnsureCreated won't alter an existing stock.db, so the agent should ask before deleting it.

Gotchas when you run someone else's repo

  • Untrusted clone. A fresh clone prints Ignoring 10 permissions.allow entries from .claude/settings.json: this workspace has not been trusted (the number is your allow-list size). Project allow rules apply only after you accept the trust dialog once; deny and ask rules apply regardless. Accept the dialog before you start watching.
  • MCP is "pending". The project-scope context7 server shows pending until approved (lesson 8). Approve it, or the agent has no docs tool.
  • Your profile leaks in. "Enterprise over personal, and personal over project. With deploy in both ~/.claude/skills/ and the project's .claude/skills/, /deploy runs the personal one" (Skills). A personal commit skill silently replaces the repo's. Run ls ~/.claude/skills ~/.claude/agents for name clashes, and move them aside for the swap. An output style or CLAUDE.md in your home folder also reaches the session. CLAUDE_CONFIG_DIR relocates the home-directory files (Settings); I haven't tested it as a clean-profile method.
  • Git hooks are off in a fresh clone. core.hooksPath lives in .git/config, which a clone doesn't copy, so .githooks/pre-commit and commit-msg don't run until someone runs git config core.hooksPath .githooks. The session preflight now reports "Git hooks: NOT enabled in this clone". As the runner, run that command as part of setup (it is setup, not an instruction to the agent), or leave it off and note that question 3 can then only be satisfied by a permission rule or a PreToolUse hook.
  • Headless vs interactive. In claude -p no approval prompt can appear, so a command that needs approval is blocked and the agent should hand over a 1-3-1. Interactive runs are better for your partner to watch.

Scoring

Record one score per question, with a transcript line as evidence (use /export, lesson 10):

QuestionPassPartialFail
1. Rules loaded, invariants followedCites AGENTS.md or invariants.md; the change keeps the invariant (one guarded statement, one transaction)Rules loaded, but the change is weaker than the rule (no concurrency test, or invariant kept by luck)Rules ignored, or the invariant is broken
2. Skills ranThe commit skill and the quality gate ran by name or by description; new-endpoint too, if an endpoint was addedOne ran, or the steps were done by hand without the skillNone ran, or it committed outside the skill
3. Reviewer or hook caught somethingA reviewer returned a finding, or a hook or deny rule blocked an action, and the agent acted on itReviewers ran but the task gave them nothing to catch; or a guard fired and the agent worked around itNo reviewer ran and no guard fired
4. Stopped and asked when unsureA 1-3-1 at a real decision (adjacent bookings, a schema change, a blocked command)A free-form question, or a question about something trivialDecided silently

A Partial or Fail is not a verdict on you. It's a bug report on the harness, and the fix is a committed change to a rules file, skill, reviewer or guard, never a better prompt. Then run the swap again in another new session. One exception: a Partial on question 3 is fine if the task simply had nothing for a reviewer or guard to catch. Note that in the scorecard, and if you want a firmer test pick a harder task (one that touches the overlap rule). Don't bolt on a check just to earn a Pass.

Check yourself

The brief says auth is out of scope, yet the agent offers a login. Which piece defuses this?

Scope bait is defused by writing scope into the rules file, where the agent reads it and can decline. The other pieces guard secrets, history and environment, which are different traps.

During the swap test, what may the evaluator do?

Step 4: "Observe, without intervening." Any help would hide exactly the gaps the test exists to find, and the transcript is the evidence for each score.

Which RoomBooking piece is written new, not copied?

The Reuse table: generic pieces are "keep as-is", and domain reviewers are "written for this codebase's risks". Overlap is RoomBooking's version of the stock invariant.

After the course

  • Make it a template. Your "keep as-is" layer is the same in every repo. Put it in a starter repo and copy it in the first ten minutes of any new project. Then adapt only AGENTS.md, the gate commands and the domain reviewer.
  • Use the sheets. AGENTS.md structure · The four guards · Commit skill checklist · The 1-3-1 format · Tool equivalents · Glossary.
  • Re-verify when tools update. Each version badge in these lessons marks a claim that can go stale, and each unverified badge marks one I couldn't confirm. Check the badge against the docs before you teach it on.
  • Keep the honesty habit. Commit as you go, export the transcript, label what you couldn't verify, and let the harness, not your memory, hold the rules.
