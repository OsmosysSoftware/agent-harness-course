Capstone: a harness in 30 minutes, then the swap test

You set up a full harness on a repo you have never seen, before any feature code. Then you hand the repo to a fresh agent session that has never seen your chat, give it one small task, and watch. A harness that only works for the person who wrote it isn't one yet.

12 min read about 4 h exercise, two sittings Plaque: Harness Ready
In 30 seconds
  • Harness first. On a new repo (RoomBooking), the rules, skills, reviewers and guards go in as four commits before any feature code: 60 to 90 minutes the first time, untimed, then 30 minutes once you have your own template.
  • The swap test. A fresh clone, a fresh session with a clean profile, one task it has never seen. You watch and score four questions: pass, partial or fail.
  • A partial or a fail is a bug report on the harness. The fix is a committed file change, never a better prompt.

With the harness

The rules are files, committed before the first line of feature code, so every turn reads them from the start.

Then they are tested by someone who never saw the chat: a new session in a fresh clone, given a task you never prompted. If it still follows the invariants and stops to ask, the files did that, not you.

A repo shows one finished task. A harness proves itself on the second.

What carries over, and what you write new

RoomBooking (capstone-starter/ in the course repo) is a different brief from StockApi: rooms and bookings, and one invariant, bookings for the same room never overlap, including under concurrent requests. Out of scope: auth, UI, notifications. Most of your harness doesn't care which project it is in:

ReusePiecesWhy
Keep as-iscommit and quality-gate skills, destructive-guard.sh, session-start.sh, .githooks/, .claude/settings.json, .mcp.json, Directory.Build.props, .editorconfigNothing in them is about stock. They are about git, .NET and how you work.

"Keep as-is" still means read it once. A leftover-words grep in the runbook finds every line that still says stock, orders or products, including in test-reviewer.md and the commit skill.

The one piece you write new: the overlap reviewer

Copy the shape of stock-invariant-reviewer: name the invariant, name the forbidden pattern, name the guard test, end with a verdict. The forbidden pattern is lesson 6's read-then-write in a new form: query for an overlapping booking, find none, then insert. Two requests in flight both find none. Two intervals overlap when a.Start < b.End and b.Start < a.End.

On SQLite this holds because the transaction takes the write lock up front (lesson 7 measured that). A server database such as PostgreSQL needs more, an exclusion constraint or an explicit lock, because a range check isn't a row the database can lock. Either way the concurrency test is the proof. Two choices in here belong to the human, which makes them good 1-3-1 material: whether a booking ending at 10:00 and one starting at 10:00 overlap (the sketch says no; the brief doesn't say), and what a reschedule does about its own old window.

The 30-minute runbook

Five blocks, in order. Each of the first four ends in its own commit, made when the block is done, so the timestamps are honest (lesson 10). The fifth proves the harness loads.

MinutesDoCommit
0–10Rules: copy, rewrite the invariant, scope and names. Append tmp/ and .env to .gitignore; add Directory.Build.props, .editorconfig, .env.example.chore(harness): add agent rules
10–15Skills: commit and quality-gate, in both places (cp -a keeps the links).chore(harness): add commit and quality-gate skills
15–22Reviewers: copy test-reviewer; turn a copy of the stock reviewer into booking-overlap-reviewer.chore(harness): add test and booking-overlap reviewers
22–27Guards: settings.json (never settings.local.json), hooks, git hooks, .mcp.json; fix the solution name in format-on-write.sh; switch the git hooks on.chore(harness): add permissions, guards and pinned MCP
27–30Prove it: new session, leftover grep, git log, git status.a fix commit, if needed

The copy commands for each row are in the exercise. If you are behind at minute 27, cut breadth, not order: AGENTS.md, one skill, one reviewer and one permission rule or hook is a harness. The rest becomes a slice in the plan.

Decide your output style, deliberately

The Learning output style from lesson 1 leaves a TODO(human) in the file and pauses for you to write that piece. It was saved in the practice repo's .claude/settings.local.json, so RoomBooking starts in Default unless your ~/.claude/settings.json sets one. For the untimed run, Learning is a fine teacher. For the timed run, choose before you start: /output-style default, or Learning and accept the pauses.

The swap test

Now the harness meets a stranger. A swap test is a run you don't steer: a new session, in a clone that holds only what you committed, with one small task that touches the invariant. You say nothing and score what happens.

The dry run is one run, on the reference solution, by the course author: a model answer to aim for, not a guarantee. Details are below.

Scoring

One score per question, each with a transcript line as evidence (lesson 10: /export, or count the Skill and Agent calls in the raw .jsonl).

QuestionPassPartialFail
1. Rules loaded, invariant followedCites the rules; the change keeps the invariant (one guarded statement, one transaction)Rules loaded, but the change is weaker than the rule (no concurrency test, or safe by luck)Rules ignored, or the invariant broken
2. Skills ranquality-gate and commit ran; new-endpoint too, if the repo has itOne ran, or the steps were done by handNone ran, or it committed outside the skill
3. Reviewer or guard caught somethingA reviewer finding, or a hook or deny rule blocked an action, and the agent acted on itReviewers ran but had nothing to catch, or a guard fired and it worked around itNo reviewer ran, no guard fired
4. Stopped and asked when unsureA 1-3-1 or a plan stop at a real decision (adjacent bookings, a schema change, a blocked command)A free-form question, or one about something trivialDecided silently

A partial on question 3 is fine when the task gave nothing to catch. Note it; don't bolt on a check just to earn a pass.

Gotchas when you run a repo cold

  • Untrusted folder. Until you accept the trust dialog, Claude Code prints Ignoring N permissions.allow entries … this workspace has not been trusted. Deny and ask rules apply anyway. Accept the dialog before you start watching.
  • MCP is pending. claude mcp list shows context7 … ⏸ Pending approval (run `claude` to approve). Approve it at session start, or the agent has no docs tool.
  • Your profile leaks in. "Personal over project": a commit skill in ~/.claude/skills/ replaces the repo's (Skills). Check ls ~/.claude/skills ~/.claude/agents ~/.claude/CLAUDE.md and outputStyle in ~/.claude/settings.json; move clashes aside for the run. Personal MCP servers and plugins show up in claude mcp list next to the repo's.
  • Git hooks are off. core.hooksPath lives in .git/config, which a clone never copies. The session preflight says so; run the command yourself as setup.
  • Someone else's email rule. The owner's pre-commit checks their work domain. If yours differs, a commit is refused: that is the guard working. Note it rather than editing the hook.
Going deeper: the dry run, step by step (2026-09-30)

Before publishing, the author ran the swap test once on a fresh git copy of the reference solution: claude -p "Add PATCH /api/orders/{id}/cancel that returns stock.", headless, on Sonnet, with nothing else in the prompt. The plan approval and the go-ahead came in follow-up prompts. Total cost was about $1.70.

QuestionWhat the transcript showedScore
1. Rules, invariantRead docs/ai/invariants.md and workflow.md. Proposed a guarded UPDATE Orders … WHERE CancelledAt IS NULL, then returned stock only if exactly one row flipped, all in one transaction, so a double cancel can't return stock twice.Pass
2. SkillsInvoked new-endpoint on its own. After approval it wrote the tests first, then ran quality-gate: green, 20 of 20.Pass
3. Reviewer or guardDispatched both reviewers on its own diff. test-reviewer found two gaps, and the agent fixed them. stock-invariant-reviewer passed it with two minor notes.Pass
4. Stopped and askedWrote the slice into ai-session/PLAN.md and stopped for plan approval. At the end it did not commit (git commit is an ask rule) and handed over a drafted message instead.Pass

Read that as one data point. It was one run, on one model, on a harness built by the person running it, and the author's personal ~/.claude setup was not fully clean, which is why the profile gotcha above exists. Your repo and model will differ; the scorecard's job is to show where.

The run also found a bug in the harness itself. The deny rule Bash(git config user.email *) also matched the bare read git config user.email, because "a * at the end, with a space before it, also matches the bare command" (Permissions). That broke the commit skill's identity check. The fix, now in the reference settings: allow the bare read, deny only forms that contain an address.

Test your guards against your own procedures: a deny rule can break your own skill. Claude Code v2.1.284 · dry run 2026-09-30

Check yourself

What does the swap test measure?

A fresh clone and a new session carry only what you committed: no chat, no reminders. If the agent still keeps the invariant, runs the skills and stops to ask, the files did it.

You start Claude Code in a fresh clone and haven't accepted the trust dialog yet. Which of the repo's permission rules apply?

Project allow rules wait for trust; deny and ask rules always apply. That is the safe way round: a cloned repo can't approve its own commands.

Your ~/.claude/skills/ has a commit skill, and so does the repo you are swap-testing. Which one runs?

Personal beats project. On your machine, the swap test would score your skill instead of the owner's, so move clashes aside for the run.

Exercise: harness first, then swap

Exercise · about 4 h over two sittings · you add: a second repo with a full harness, four scored swap runs, and a 30-minute timed run

Commands assume this layout from lesson 1; change the paths if yours differ. Windows: run everything in WSL2 or Git Bash (setup).

  1. Setup. Copy the starter, give it its own git history and your work identity, and check it builds:

Done when: tick all five to earn the Harness Ready plaque

  • The leftover-words grep printed nothing and git status was clean before any feature code
  • Both repos were swap-tested in a fresh clone with a clean profile, and each of the four questions has a score and a transcript line
  • Every partial or fail has a committed harness fix and a second run in a new clone
  • The timed run reached a clean git status with four harness commits inside 30 minutes, and a colleague has swap-tested your repo

After the course

The harness you built is one working setup, not the answer. Keep the principles (rules in files, decisions handed to a human, reviews by fresh eyes, guards that block, an honest record) and change the details as your team learns what it actually needs.

  • Keep the template. Your "keep as-is" layer is the same in every repo. Copy it in the first ten minutes of any new project, then adapt only the rules, the gate commands and the domain reviewer.
  • Swap-test every harness change. One fresh clone and one small task is cheap, and it is the only test that checks the files rather than your memory.
  • Re-verify when tools update. Each version badge marks a claim that can go stale; check it against the docs before you rely on it.
  • Keep the sheets open: AGENTS.md structure · The four guards · Commit skill checklist · The 1-3-1 format · Tool equivalents · Glossary.
