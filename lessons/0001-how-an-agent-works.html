Agent Harness · Lesson 1 of 11 · 20 min read + 30 min exercise

How a coding agent actually works

The agent is a loop that re-reads its context window every turn, and that window is all it knows. Once you see that, it's clear why a rule typed into the chat fades, while a rule in a file keeps steering.

The win

By the end you'll have the practice repo under git with your company identity. You'll also have shown yourself, in about two minutes, that a rule given only in chat is gone after /clear.

Words you'll meet

Five words carry this course. Each is explained properly later; for now, one plain clause each (all in the glossary).

  • Harness: the agent tool plus the files in your repo that configure it.
  • Rule: an instruction written in a file the agent reads, so it does not depend on chat.
  • Skill: a saved, named procedure the agent follows when you call it.
  • Reviewer: a second agent that checks the first one's work with a fresh mind.
  • Hook or guard: a script or rule that blocks an action before it runs, rather than asking nicely.

What the harness does instead

The rules go in a file that the tool loads at the start of every session and re-reads from disk after compaction. Rules about commits are backed by something that blocks, not something the agent is asked to remember.

That's the whole course: move each rule out of the chat and into the layer that can't forget it.

The loop

An agent is a model in a loop with tools. The tools are functions it may call: read a file, edit a file, run a shell command, search, fetch a URL. Each turn, the model reads its whole context and chooses the next tool call. The harness runs the call and appends the result, and the model reads everything again. Anthropic describes three repeating phases: gather context, take action, verify results (How Claude Code works).

Two consequences matter for the rest of the course:

  1. The model has no memory outside the window. Anything it "knows" about your project is either in its training data (stale, generic) or in the window right now.
  2. The harness sits between the model and your machine. Every tool call passes through it, so that's where things can be blocked, not just requested. Harness means the tool (Claude Code, Codex, Antigravity) plus everything in your repo that configures it: rules, skills, reviewers, hooks and permissions.

The context window, and why prose rules drift

The context window is the model's working memory, and it's finite. It holds the system instructions, your rules files, loaded skills, the conversation, and every file and command output so far (Context window). In a long session it fills up. Claude Code then compacts: it summarises older turns to make room. Run /context to see what's using the space, /compact to compact on demand, and /clear to start fresh.

What survives compaction is documented. The difference between the two rows below is the core reason for a harness:

Where the rule livesAfter /compactAfter /clear or a new session
Project-root CLAUDE.md / AGENTS.mdRe-read from disk and re-injectedLoaded again
Your message in the chatSummarised; details may be lostGone

The docs name the causes when a rule goes missing after compaction: it "was given only in conversation, lives in a nested CLAUDE.md that hasn't reloaded yet, or is a path-scoped rule that hasn't matched a file since" (Memory). Trainee A's 17k-character prompt was a conversation message in a 356-turn session: exactly the kind of instruction compaction summarises.

Permission modes and plan mode

A permission mode decides which tool calls run without asking you. In Claude Code, Shift+Tab cycles through them, and permissions.defaultMode sets the starting one. The table follows the official one (Permission modes):

ModeWhat runs without askingUse it for
default (shown as "Manual")Reads onlyReviewing every action yourself
acceptEditsReads, file edits, common filesystem commandsA slice you have planned and approved
planReads, plus classifier-approved commands when auto mode is available; no source edits until you approve a planExploring and planning (lesson 4)
autoEverything, with background safety checks by a classifier modelLong, lower-risk work
bypassPermissionsEverythingIsolated containers and VMs only

Check which mode you start in. On Claude Code v2.1.283 or later you start in auto, where a second model approves most actions for you. That is why a commit or an app launch can happen without a prompt, unless your repo says otherwise. v2.1.283+ · verified 2026-09-30

Going deeper: the classifier, deny rules and ask rules

The docs: "With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions". The classifier is that second model; it checks each action in the background. Two things still hold in every mode: a deny rule (a line in your settings saying "never run this") always blocks, and an ask rule ("always check with me first") still prompts "even in auto mode" (Permissions). Lesson 7 writes both.

Clicking "Yes, and don't ask again" saves an allow rule (a line that lets that command run without asking) in .claude/settings.local.json, your personal file. Trainee B copied such a pile of clicked approvals into the shared .claude/settings.json. It held rules that let the agent rewrite git history and delete files, and was then credited as "AI configuration". An allow-list you clicked together isn't a policy. Lesson 7 writes a real one.

One setting for this course: the Learning output style

An output style changes how Claude Code talks to you, not what it knows about the repo. The built-in Learning style writes the routine code itself. At real design decisions it leaves a TODO(human) for you to write a few lines, and it explains its choices in Insight blocks (Output styles). Turn it on for the whole course with /output-style learning. It's saved to .claude/settings.local.json, which isn't committed, so it's a personal setting and not part of your harness. It's Claude Code only; Codex and Antigravity have no equivalent as of 2026-09-30.

Check yourself

You told the agent in chat, 200 turns ago, "never commit without asking". It just committed. What is the most likely cause?

Chat instructions are summarised during compaction; only files like AGENTS.md / CLAUDE.md are re-read from disk. Auto mode then let the commit run without a prompt. And even a remembered instruction is only a request, so lesson 7 makes "ask before commit" a permission rule.

Where can a tool call be stopped regardless of what the model "wants"?

Everything the model reads is a request. The harness runs the call, so the harness is where permission rules and hooks can refuse it.

A trainee commits .claude/settings.local.json full of approvals they clicked. What is it?

"Don't ask again" writes to settings.local.json, which is personal and meant to be git-ignored. A policy is written on purpose, reviewed, and lives in .claude/settings.json.

Exercise: set up the practice repo and watch a chat rule vanish

Exercise · ~30 min · adds: a git repo with the right identity
  1. Get the two repos. The course repo holds the reference solution and the capstone starter, which later lessons copy from. The practice repo is yours to change. Use the same folder for every lesson: 
    mkdir -p ~/projects && cd ~/projects
git clone https://github.com/OsmosysSoftware/agent-harness-course.git
git clone https://github.com/OsmosysSoftware/agent-harness-practice.git stockapi
cd stockapi && rm -rf .git
    The last line removes the template's history, so the next step starts your own repo under your company identity. Windows: run these in WSL2 or Git Bash (see Before you start on the index).
  2. Set your identity for this repo and make the starter commit: 
    git init -b main
git config user.name "Your Name"
git config user.email you@osmosys.co
git add . && git commit -m "chore: import StockApi starter"
    Five of the six reviewed repos had AI trailers (a line an agent adds at the end of a commit message naming itself as co-author) or personal emails in their history. The identity is set once, here, not by the agent.

    Conventional Commits is the message format this course uses: type(scope): short summary, where the scope is optional. Common types: feat (new behaviour), fix (a bug), docs, test, refactor, chore (housekeeping). chore(harness): add agent rules is one. Spec: conventionalcommits.org.

  3. Check it builds: dotnet build and dotnet test (4 tests, green).
  4. Start your agent in the repo. In Claude Code, press Shift+Tab until the line under the input box says plan mode on (if nothing changes, try Alt+M). Then type /output-style learning in the chat box and press Enter. Anything starting with / is a Claude Code command, not a message to the model.
  5. Ask: "Explain how an order reduces stock in this repo, citing file:line." Then run /context and note which categories use the most space.
  6. The drift experiment. Tell it: "From now on, end every answer with the word STOCK-OK." Ask any question and confirm it complies. Now run /clear and ask again. The rule is gone. (If it survived, run /memory, which lists the files Claude keeps notes in: auto memory saved your rule to a file, which proves the point.)
  7. Write down, in one sentence, where that rule would have to live to survive. Lesson 2 puts it there.

Codex: run codex with the default approvals. Antigravity: open the folder and use the Default preset. Steps 5–7 work the same way; start a new conversation instead of /clear.

Done when
  • git log --format='%an <%ae>' shows your company email, and no AI trailer
  • dotnet test is green
  • You saw STOCK-OK disappear after /clear
