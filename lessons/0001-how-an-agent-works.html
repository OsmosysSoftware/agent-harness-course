How a coding agent actually works

The agent re-reads one context window every turn, and that window is all it knows. A rule typed into the chat fades from it; a rule in a file keeps coming back.

15 min read 30 min exercise Plaque: Loop Reader
In 30 seconds
  • An agent is a loop: read the context, pick a tool call, get the result, repeat.
  • Rules in files survive long sessions. Rules typed in chat can be summarised away.
  • The harness sits between the model and your machine, so that's where actions can be blocked.

With the harness

The rules live in a file the tool loads at the start of every session and re-reads after compaction.

"Don't commit without asking" becomes a rule the tool enforces: it has to ask you first, whatever the agent remembers.

That's the whole course: move each rule out of the chat and into a layer that can't forget it.

The loop

An agent is a model in a loop with tools: functions it may call, like read a file, edit a file or run a command (How Claude Code works). Watch one turn:

Two things follow. Apart from its training, the model knows only what is in that window. And because every tool call passes through the harness, the harness is where you can block, not just ask.

Managing the context window

The context window is the model's working memory, and it has a size limit. When it fills up, Claude Code compacts it: older conversation is replaced by a short summary. Try it:

0% full
rules file (re-read from disk) rule typed in chat messages and tool results

So: a rule that matters goes in a file, never only in chat. And you choose what happens to the window, instead of waiting for automatic compaction:

Nothing is wrong, so change nothing. Every summary or fresh start loses some detail; carrying on is the only move that keeps the conversation exactly as it happened.

Answers are getting vague after a long session. Before you choose anything, you want to see whether old test output is what's taking up the space.

Going deeper: exactly what survives compaction

From the docs (Context window, verified 2026-10-01):

  • Re-read from disk: the project-root CLAUDE.md or AGENTS.md, unscoped rules, auto memory, and the plan from plan mode.
  • Reloaded only when a matching file is read again: rules with paths: and nested rules files. To make a rule survive, keep it in the root file.
  • Re-injected but capped: skills you used, 5,000 tokens each. Put a skill's most important lines at the top.
  • Up to five recently edited files are re-read. Everything else in the conversation becomes the summary.

You can also set when it happens (/autocompact) or summarise part of a conversation with /rewind.

Which mode are you in?

A permission mode decides which actions run without asking you. Press Shift+Tab to cycle through them (Permission modes).

defaultAsks before almost everything ("Manual")
acceptEditsEdits files freely, asks for commands
planReads and plans; no edits until you approve
autoA second model approves most actions
bypassNever asks. Sandboxes only
Asks you moreAsks you less

On Claude Code v2.1.283 or later you start in auto verified 2026-09-30. That is why a commit or an app launch can happen with no prompt, unless your repo says otherwise: an ask rule in its permission settings still prompts even in auto mode, whatever the model decides. Lesson 7 writes those.

Going deeper: deny rules, ask rules, and a clicked-together allow list

Two things hold in every mode. A deny rule in your settings always blocks, and an ask rule still prompts "even in auto mode" (Permissions). Lesson 7 writes both.

Clicking "Yes, and don't ask again" saves an allow rule to your personal .claude/settings.local.json. One developer copied a pile of those into the shared .claude/settings.json, including rules that let the agent rewrite git history, and called it their "AI configuration". An allow list you clicked together isn't a policy.

New to the words? Five you'll meet all course
  • Harness: the agent tool plus the files in your repo that configure it.
  • Rule: an instruction in a file the agent reads, so it doesn't depend on chat.
  • Skill: a saved, named procedure the agent follows when called.
  • Reviewer: a second agent that checks the first one's work with fresh eyes.
  • Hook or guard: something that blocks an action before it runs, instead of asking nicely.

All terms: glossary.

Check yourself

You told the agent in chat, 200 turns ago, "never commit without asking". It just committed. What is the most likely cause?

Chat instructions get summarised during compaction; only files like AGENTS.md are re-read from disk. Auto mode then let the commit run. Even a remembered instruction is only a request, so lesson 7 makes "ask before commit" a rule the harness enforces.

Where can a tool call be stopped regardless of what the model "wants"?

Everything the model reads is a request. The harness runs the call (step 4 in the diagram), so that's where permission rules and hooks can refuse it.

A developer commits .claude/settings.local.json full of approvals they clicked. What is it?

"Don't ask again" writes to settings.local.json, which is personal and meant to stay out of git. A policy is written on purpose, reviewed, and lives in .claude/settings.json.

Exercise: set up the repo, then watch a chat rule vanish

Exercise · about 30 min · you add: a git repo with your work identity
  1. Get the two repos into one folder. Windows: use WSL2 or Git Bash (setup). 
    mkdir -p ~/projects && cd ~/projects
git clone https://github.com/OsmosysSoftware/agent-harness-course.git
git clone https://github.com/OsmosysSoftware/agent-harness-practice.git stockapi
cd stockapi && rm -rf .git
    The last line drops the template's history, so your repo starts clean.
  2. Start your own history under your work identity: 
    git init -b main
git config user.name "Your Name"
git config user.email you@yourcompany.com
git add . && git commit -m "chore: import StockApi starter"
    Commit messages in this course use Conventional Commits: type(scope): summary, where type is feat, fix, docs, test, refactor or chore.
  3. Check it builds: dotnet build, then dotnet test (4 tests, green).
  4. Start Claude Code in the repo. Press Shift+Tab until it says plan mode on. Then type /output-style learning: it makes Claude explain its choices and leave small design decisions for you to code.
  5. Ask: "Explain how an order reduces stock in this repo, citing file:line." Then run /context to see what fills the window.
  6. The drift test. Say "From now on, end every answer with STOCK-OK." Ask anything and check it complies. Run /clear to start a new chat and ask again: the rule is gone. (Still there? Run /memory: auto memory saved it to a file, which proves the point.)
  7. Write one sentence: where would that rule have to live to survive? Lesson 2 puts it there.

Codex: run codex with default approvals. Antigravity: open the folder with the Default preset. In step 6, start a new conversation instead of running /clear.
