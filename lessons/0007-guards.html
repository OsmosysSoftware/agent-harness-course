Guards: rules that block instead of asking

A rule is text the agent may follow. A guard is code that runs on the action and refuses it, so the four kinds below, stacked, make the important rules hold even when the agent forgets, or the human asks it to break them.

Rule versus guard

A rule is an instruction in the agent's context: AGENTS.md, a skill step, your chat message. The model reads it and usually complies, and Trainee A's unasked commit shows what "usually" costs. A guard is code that runs when the action happens and can refuse it. The four kinds differ in reach: what they see, and who is stopped.

Four terms first. You'll meet them in the table and again below.

  • Hook: a script the tool or git runs automatically when something happens, such as "a command is about to run" or "a commit is about to be recorded". Like a database trigger, but for your workflow.
  • stdin: the input stream a program reads. A hook script doesn't get arguments; the tool pipes the details to it as text (here JSON) on stdin.
  • Exit code: the number a script finishes with, like a process's return value in C#. 0 means "fine"; what a non-zero value means depends on who is listening (the lesson spells it out for each).
  • core.hooksPath: a git setting that tells git which folder holds your hooks. Until it is set in a clone, git looks in its default .git/hooks and ignores the committed .githooks/ folder.

Stack them. Each has a hole the next one covers, and none of them is a security boundary against a determined person.

1 · Permission rules

A permission rule is an entry in allow, ask or deny that matches a tool call. "Rules are evaluated in order: deny, then ask, then allow. The first match … determines the outcome", and an allow rule can't carve an exception out of a deny (Permissions). This is the reference solution's file, verbatim:

  • allow is the boring, frequent and safe: build, test, format, read-only git, the gate script, and sqlite3 -readonly -safe (lesson 8 explains it). git add * is allowed because staging is reversible and the commit itself is still gated.
  • ask is where a human must say yes: git commit (the skill's step 6 becomes real), push, rebase, reset, restore, dotnet add (a new package needs the 14-day check: Osmosys's house rule is that no package version younger than 14 days is added, a supply-chain precaution, because poisoned releases are usually caught within days of publishing) and rm.
  • deny cannot be approved from a prompt: the force-push forms, --no-verify (which would skip the git hooks below), reading or editing .env, and setting the git email. Deny rules from any settings scope beat allow rules, so a trainee's local allow cannot undo them.

What a rule does not do

  • It matches text. A Bash rule "matches the command text Claude writes", after splitting compound commands (a && b is checked part by part) and stripping wrappers. It "isn't a security boundary around the program": a different spelling of the same operation can slip past. That's why the same operations also appear in a hook and in a git hook.
  • A trailing wildcard also matches the bare command. The docs say "a * at the end, with a space before it, also matches the bare command". The first version of this file denied Bash(git config user.email *), meaning to stop the agent setting a personal email. It also blocked reading the email, which step 4 of the commit skill does, and a swap-test dry run stopped at that step. The fix, now in the file, is Bash(git config user.email *@*) (two wildcards, so the bare read doesn't match) plus an allow for the bare read. Test your guards against your own skills: run each skill once after you add a rule.
  • The auto-saved list is not a policy. Trainee B's git rebase * entry was a click, never a decision. Every line above was decided, and the decision is in a reviewed file.

The attribution setting

The same file carries "attribution": {"commit": "", "pr": "", "sessionUrl": false}. It stops Claude Code adding a Co-Authored-By trailer to commits and a "generated with" line to pull requests, the two things that showed up in the repos. The 11 of 13, 12 of 13 and 6 of 7 counts (Trainee A, Trainee B, Trainee D) are commits carrying a Co-Authored-By trailer; they do not include PR lines. Use exactly this object form: it is the one every Claude Code version reads.

Going deeper: why the object form, and what workspace trust changes

This is the portable form. The shorter "attribution": false needs v2.1.281+ · verified 2026-09-30, and "older versions skip the whole settings file that contains it" (Settings reference). On an older install, your deny rules and hooks silently disappear too, and nothing tells you. Use the object form, which every version reads. The old includeCoAuthoredBy key has been deprecated since v2.0.62.

  • Allow rules need workspace trust (the "do you trust this folder?" dialog); deny and ask do not. verified 2026-09-30 In a fresh clone run headless (with nobody at the keyboard, so no trust dialog), Claude Code printed "Ignoring 10 permissions.allow entries from .claude/settings.json: this workspace has not been trusted" (the number is your allow-list size). Your guards protect even an untrusted clone. The convenience rules wait for the trust dialog.

2 · PreToolUse hooks

A hook is a script the harness runs at a named event. A PreToolUse hook runs before a tool call, receives the call as JSON on stdin, and can deny it. Use one where a permission pattern isn't expressive enough: several forms of one idea, or a message that teaches the agent what to do instead. The hook is registered in settings.json (see the hooks block above) with a matcher of Bash.

Three things to learn from it (Hooks reference):

  • Two ways to block. The script above prints a JSON permissionDecision: "deny" with a reason and exits 0. The alternative is exit 2, where stderr becomes the reason. Exit 2 "blocks whether or not you print JSON".
  • Exit 1 does not block. "For most hook events, exit code 2 is the only exit code that blocks through the code alone. Without valid JSON on stdout, Claude Code treats exit code 1 as a non-blocking error and proceeds with the action." This is the opposite of a git hook, where any non-zero exit blocks. It is the classic mistake when porting a script.
  • Silence is not approval. "Exit 0 with no output means the hook has no decision", so the call goes on to the normal permission flow. The last line of the script is exit 0 for that reason. A hook also can't override your rules: a matching deny or ask rule still applies whatever the hook returns.

The failure to watch for is a hook that can't start. If "the script path doesn't exist or isn't executable", the shell exits with 127, the action proceeds, and "a mistyped path in settings.json leaves the gate silently disabled". Watch for the "non-blocking status code" notice the first time you run it. The registration in the file above runs the script through bash, so it doesn't need the executable bit, but it does need the right path (${CLAUDE_PROJECT_DIR}).

The script greps raw JSON text, which is crude. A commit message that mentions "git rebase" would trip it. That's an accepted cost: a false alarm sends the agent back to you, and a miss would be worse.

So don't write the words rebase, rm -rf or --amend in a commit message: the hook reads the whole command, so git commit -m "docs: mention git rebase" is denied. Use the messages this lesson suggests.

Scope. The matcher is Bash, so this hook sees shell commands only. An agent that edits a .csproj with its Edit tool never reaches it; the "net8.0" invariant in AGENTS.md and the reviewers cover that, and the hook only catches the shell spelling. Windows: the registered command is bash "${CLAUDE_PROJECT_DIR}/…", which assumes the Bash tool (WSL2 or Git Bash, as on the index). Run probe 1 below to prove it fires on your machine. unverified: the ${CLAUDE_PROJECT_DIR} path form on Windows was not tested

SessionStart and PostToolUse, briefly

Hooks aren't only for blocking. SessionStart runs when a session opens, and its plain stdout is added to the agent's context. The course uses it for a preflight that reports and never fixes: the answer to Trainee A's agent launching Docker Desktop and polling for 35 minutes. PostToolUse runs after a tool call. The course formats the C# file the agent just wrote, so the quality gate's format step isn't the first to notice whitespace. Neither one blocks anything.

Going deeper: the two scripts (you still add both in the exercise)

The session-start script also reports whether core.hooksPath is set in this clone, which is the "put it in the preflight" advice below.

3 · Git hooks

Permission rules and Claude hooks exist only inside Claude Code. A commit made by Codex, by Antigravity, or by you in a terminal goes through git, so git is where a check must live to cover all of them. A git hook is an executable file that git runs at a step: pre-commit before a commit is recorded, commit-msg once the message is written. A non-zero exit aborts the commit. Two setup facts decide whether they work at all (githooks):

  • Hooks must be executable: chmod +x .githooks/pre-commit .githooks/commit-msg. (Windows: run shell commands in WSL2 or Git Bash, see Before you start on the index. In Git Bash chmod changes nothing git records, so also run git update-index --chmod=+x .githooks/pre-commit .githooks/commit-msg .claude/hooks/*.sh after git add, or a Mac or Linux colleague gets hooks that silently never run. Your repo already has a .gitattributes that keeps these files LF, which bash needs.)
  • The setting is per clone. git config core.hooksPath .githooks is stored in .git/config, which isn't committed. Every fresh clone starts with the hooks switched off until its owner runs that command. Put it in the README and in the session-start preflight.

Why a shell regex and not commitlint

The usual tool is commitlint, but its newest release was under 14 days old when this lesson was checked, which the house rule (no package version younger than 14 days) rules out, and it would need Node in a .NET repo. A 20-line shell regex has no dependency and runs in any clone. The trade-off: it checks the subject shape only, and you write the allowed types yourself.

Going deeper: the commitlint dates

On 2026-09-30 commitlint's current release (@commitlint/cli 21.2.3) was 11 days old. Recent releases are the ones supply-chain attacks target, which is the reason for the rule.

Two honest gaps

  • If gitleaks isn't installed, the hook runs the pattern check only and prints a warning. Installing software is your decision, not the agent's (lesson 3): see the gitleaks install page, check the release date first, and if you can't install it, do the pattern half only and carry on. The pinned command is gitleaks git --pre-commit --staged.
  • One scanner is not a secret policy. gitleaks misses readable, low-entropy secrets such as Trainee C's "Key": "SuperSecretAuthenticationKeyForFulfillmentService2026!", so the hook first runs the pattern check and then gitleaks. You'll see the miss yourself in probe 3.
Going deeper: what we measured, and the pattern check's limits

gitleaks 8.23.3 and 8.30.1 · measured 2026-09-30 gitleaks git --pre-commit --staged found no leak, on both versions, in Trainee C's actual string, because the value is readable words with low entropy. Both versions did flag a random 32-character key. So step 3 of the hook first runs a pattern check for config-style secrets (a key, secret, password or token name followed by a quoted value of 8 or more characters), then gitleaks for known key formats. The commit skill's step 3 runs both checks too. The pattern is crude: it will occasionally flag a harmless line, and then the human decides. Also keep the deny rule on .env and the invariant "no secrets in tracked files". The older gitleaks detect and protect commands have been deprecated since v8.19.0.

Git hooks have one more hole: git commit --no-verify skips them. The deny rules above stop the agent typing it; you can still type it. A server-side check (CI, branch protection) is the real backstop, and out of scope here. GitLab's branch protection is what saved Trainee A's remote branch. Note what the local layer does not cover: this repo has no pre-push hook, so a human typing git push --force in a terminal is stopped only by the server. The local deny covers the case in the incident: the human asking the agent.

4 · Guard tests

The first three guards stop an action. A guard test is an automated test that encodes a project rule, so a change that violates it fails the build. The evaluator's probe for the stock invariant is the model: 12 simultaneous orders for a product with 3 in stock must give exactly 3 created, 9 conflicts and 0 stock left.

  • gate.SetResult() releases all 12 requests together. Without the TaskCompletionSource gate they would start one after another and rarely overlap.
  • Your ApiTests has a private CreateProductAsync; the new test needs the same helper, so the agent should move it to a shared TestHelpers file rather than copy it (DRY: one helper, two users).
  • It uses FileStockApiFactory, a real SQLite file in a temp folder, because one shared in-memory connection isn't thread-safe. EF InMemory is out for the reasons in docs/ai/testing.md.
  • It asserts on the state too (stock is 0), not just status codes.

A guard test can be green for the wrong reason. We measured it. Read-then-write inside BeginTransactionAsync() passes this test on SQLite, because Microsoft.Data.Sqlite's transaction takes the write lock up front. The test fails, with Assert.Equal() Failure: Expected: 3, Actual: 12 (all 12 orders created), only when the transaction is also removed, which is what an InMemory-driven rewrite does. On SQL Server at READ COMMITTED, the transaction version oversells. So the test catches the regression an InMemory rewrite produces, and the stock-invariant reviewer from lesson 6 catches the design. You need both.

Fuller comparison: Tool equivalents.

Check yourself

A trainee commits from a plain terminal. Which guard still runs?

Permission rules and Claude hooks run only inside Claude Code, and skills run only when an agent loads them. Git hooks run for anyone who commits in a clone that has core.hooksPath set.

A Claude Code PreToolUse hook script exits with status 1. What happens?

Without valid JSON, exit 1 is a non-blocking error and the action proceeds. Only exit 2, or a JSON deny, blocks. Git hooks differ: any non-zero exit aborts the commit.

Why is the commit-msg hook a shell regex, not commitlint?

The house rule bars any package version younger than 14 days, and commitlint's newest release was younger than that. It would also add Node to a .NET repo. A shell regex has no dependency and works in any clone, at the cost of checking the subject shape only.
