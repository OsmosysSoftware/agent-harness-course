Guards: rules that block instead of asking

A rule in AGENTS.md is a request: the agent usually follows it. A guard is code that runs on the action itself and refuses it, whoever forgot the rule and whoever asked.

Rule versus guard

The docs put it plainly: rules in your prompt or CLAUDE.md "shape what Claude tries to do, but they don't change what Claude Code allows" (Permissions). A guard is code that runs when the action happens and can refuse it. Four terms, once:

  • Hook: a script a tool or git runs automatically at a named moment ("a command is about to run"). Like a database trigger, for your workflow.
  • stdin: the input stream a program reads. Claude Code sends a hook the tool call as JSON on stdin.
  • Exit code: the number a script ends with; 0 means fine. Claude Code and git read non-zero codes differently (below).
  • core.hooksPath: the git setting naming your git hooks folder. It lives in .git/config, which is never committed, so every clone sets it.

The stack you build today, and which layer stops which bad action:

1 · Permission rules

A permission rule matches a tool call by its text: allow (no prompt), ask (you say yes) or deny (refused, in every mode). Deny is checked first, then ask, then allow; the first match wins.

  • ask covers commit, push, history changes, deletes and dotnet add. A new package gets the course's 14-day rule, a supply-chain precaution: no package version younger than 14 days, because poisoned releases are usually caught within days.
  • deny can't be approved from a prompt: force-push, --no-verify (skips git hooks), .env, changing your git email.
  • attribution stops the Co-Authored-By trailer on commits and the "generated with" line on pull requests. Keep the object form: false needs v2.1.281+, and older versions skip the whole file, deny rules included. verified 2026-10-01

Limits. A Bash rule matches text, so it "isn't a security boundary around the program": another spelling can slip past, which is why force-push is also in the hook. A trailing * also matches the bare command: denying Bash(git config user.email *) would block the commit skill's plain read of the email, hence *@*. And project allow rules wait for the "trust this folder" dialog; deny and ask rules apply anyway.

2 · The PreToolUse hook

A PreToolUse hook runs before a tool call. It gets the call on stdin, for example {"tool_name":"Bash","tool_input":{"command":"git push --force origin main"}}, and can refuse it with a reason that tells the agent what to do instead. The course's destructive-guard.sh refuses force-push, history rewrites, recursive deletes, dropping the database, starting or installing software, and leaving net8.0. One of its checks:

deny prints a JSON "permissionDecision":"deny" and exits 0 (exit 2 also blocks). From the hooks reference:

  • Exit 1 does not block. Claude Code "treats exit code 1 as a non-blocking error and proceeds with the action". In a git hook, any non-zero exit blocks: the classic porting mistake.
  • Silence is not approval. Exit 0 with no output means no decision; your permission rules still apply, and a hook can't override them.
  • A hook that can't start is off. "A mistyped path in settings.json leaves the gate silently disabled." Watch for a "non-blocking status code" notice.

Scope: the matcher is Bash, so edits made with the Edit tool never reach it. It greps the whole command, so even a commit message mentioning git rebase is refused; a false alarm is the cheap way to fail. The same block registers two helpers that never block: a SessionStart preflight the agent reads at the start, and a PostToolUse formatter for C# files.

3 · Git hooks

A commit made by Codex, Antigravity or you in a terminal never passes through Claude Code, but it always passes through git. A git hook is an executable file git runs at a step: pre-commit before the commit is recorded, commit-msg once the message is written. Any non-zero exit aborts the commit.

HookRefuses
pre‑commitStaged bin/, obj/, tmp/, .db or .env · an author email outside your work domain · a config-style secret (a pattern check, then gitleaks if installed) · formatting drift
commit‑msgA subject that isn't type(scope): summary · a Co-Authored-By trailer naming an AI tool, or a "generated with" line

Why two secret checks: we measured that gitleaks 8.23.3 and 8.30.1 both miss a readable key like SuperSecretAuthenticationKeyForFulfillmentService2026!, the kind a real session committed. It looks like words, not noise. The pattern check catches it; you'll see this in probe 3.

Holes: the hooks run only in a clone that ran git config core.hooksPath .githooks, only if executable, and git commit --no-verify skips them. The deny rule stops the agent typing that; you still can. Server-side checks (CI, branch protection) are the real backstop, as the incident showed.

4 · The guard test

The first three guards stop an action. A guard test stops a result: a test that encodes an invariant, so breaking it fails the build. Yours sends 12 one-unit orders at once for a product with 3 in stock: exactly 3 created, 9 refused with 409, stock 0. The requests wait at a gate (a TaskCompletionSource) so they really overlap, on real SQLite in a temp file, because the shared in-memory connection isn't thread-safe.

Know what it proves. We measured: read-then-write without a transaction fails it (Expected: 3, Actual: 12). Inside BeginTransactionAsync() it passes, because SQLite's transaction takes the write lock up front. That green is about SQLite, not the design. The test catches the regression; the lesson 6 reviewer catches the design.

Check yourself

You commit from a plain terminal, with no agent running. Which guard still runs?

Permission rules, Claude Code hooks and skills live inside the agent. Git hooks run for anyone who commits, in a clone with core.hooksPath set.

A Claude Code PreToolUse hook prints nothing and exits with status 1. What happens to the tool call?

Exit 1 is a non-blocking error; the call proceeds to your permission rules. Only exit 2 or a JSON deny blocks. In a git hook, any non-zero exit blocks.

Read-then-write inside a transaction passes the 12-for-3 test on SQLite. What catches it?

That green proves SQLite's locking, not the design. The reviewer reads the diff and blocks read-then-write even when the suite is green.
