The four guards

Rule vs guard, and the four mechanisms that mechanically block: permission rule, PreToolUse hook, git hook, guard test. Where each lives, what it stops, who it binds. They are one working set: if your team already has CI checks or branch protection doing the same job, keep those and fill the gaps.

Rule vs guard

In this course a guard always means something that mechanically blocks. A rule the agent is asked to follow is a rule. A rule is a request in the context window; a guard sits where the call runs, so it holds after compaction, after /clear, and when the model "wants" otherwise. Write the rule too, so the agent stops walking into the wall.

1 Permission rule

No script. The tool refuses or prompts. Hand-written, reviewed and committed, unlike the auto-saved settings.local.json.

Evaluated deny, then ask, then allow; the first match decides (Permissions). Compound commands are split and each part matched. Deny and ask always apply; project allow rules apply only after workspace trust.

3 Git hook

Runs for anyone committing. Enable once per clone; hooks must be executable.

Secret scanning runs a pattern check and gitleaks: gitleaks 8.23.3 and 8.30.1 both did not flag the low-entropy "SuperSecretAuthenticationKey..." value, and both flagged a random 32-character key (measured 2026-09-30); the pattern check does. No Node needed: a shell regex. @commitlint/cli 21.2.3 was 11 days old on 2026-09-30, inside this course's 14-day rule for new packages (supply-chain attacks target fresh releases). Nothing forces core.hooksPath; the deny rule on the no-verify flag covers the agent.

2 PreToolUse hook

A script that reads the call and can deny it. Wiring, then the script:

Block with exit 2 (stderr becomes the reason) or exit 0 with JSON permissionDecision: "deny". Exit 0 with no output is "no decision", not approval, and a hook cannot override a deny or ask rule (Hooks).

4 Guard test

A test for a project rule; the only guard that checks behaviour, not text.

Measured 2026-09-30: read-then-write inside BeginTransactionAsync() still passes on SQLite (Microsoft.Data.Sqlite takes the write lock up front); without the transaction it fails with "Expected: 3 / Actual: 12". A green guard test can be green for the wrong reason, so a reviewer agent reads the diff as well.

Cautions

  • A Bash rule isn't a security boundary. It matches the command text the agent writes, not what the program does. A deny on git push --force* will not see a wrapper script. That is why the guard hook greps the same patterns, and why git hooks and branch protection sit behind them.
  • A trailing space-star also matches the bare command. The first draft denied Bash(git config user.email *); it blocked reading the email and broke the commit skill's identity check. Fixed with two wildcards, which do not match the bare command, plus an allow for the bare read: deny Bash(git config user.email *@*), allow Bash(git config user.email). Test every guard against your own procedures.
  • Allow rules need trust; deny and ask do not. In an untrusted clone Claude Code prints "Ignoring 10 permissions.allow entries from .claude/settings.json: this workspace has not been trusted" (the number is your allow-list size). Deny and ask still apply. verified 2026-09-30
  • Silence is not consent. A hook that prints nothing decides nothing; the normal permission flow continues.
  • Probe every guard once. Ask for the forbidden thing and watch it refuse: force-push; "Update the changes"; a fake key in appsettings.json; read-then-write with the transaction removed.
