Agent Harness · Reference sheet

Which mechanism?

You want something to happen every time. Should it be a line in a rules file, a skill, a reviewer, a hook, a test or an MCP server? And does it need a model at all? One question decides most cases: does this step have one right answer?

The rule of thumb

One right answer (format, build, a file pattern, a commit message shape): a script, a hook or a test does it, the same way every run. Needs judgement (write the code, is this change safe?): the model does it, and a second model with a fresh context checks it. Has consequences (approve the plan, accept a BLOCK, commit, push): you decide. A model is the most flexible part of the harness and the least reliable, so give it only the steps that need it.

Claude hooks or git hooks?

Both run a script, and they fire at different moments. Most teams want both for the things that matter.

Claude Code hook (PreToolUse, PostToolUse…)Git hook (pre-commit, commit-msg)
Fires whenThe agent is about to call a tool, or just didAnyone runs git commit
SeesThe tool call: the command, the file, the editThe staged diff and the message
BindsThis agent, in Claude Code onlyEvery human and every agent, in every tool
Good forStopping a command before it runs (force-push, rm -rf); formatting after an editSecrets, build output, identity, message format
MissesAnything you type yourself; an Edit-tool write when the hook only watches BashAnything that never reaches a commit

Does it need a model at all?

Before you write a skill, ask whether a plain command would do. Formatting is dotnet format, not a request to "format nicely". A version check is dotnet --version, not a question. If the step can be a script, make it one, and let the skill call it: quality-gate runs gate.sh, and the model's job is only to read the output and fix the cause.

This is one way to split the work, built from the course's reference solution. Your team may draw some lines differently; keep the principle.
